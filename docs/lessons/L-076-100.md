# Lessons — shard 4: L-076…L-100

Append-only lesson log, **25 entries per shard** (D-023). Rules and index live in
`docs/LESSONS.md`. Entries are never edited.

---

### L-076 — Options types asserted with `shouldBe` need value equality `process`
Adding a `decompiler: DecompilerEngine` field to `BodyOptions` broke every CLI
test that captures options with `shouldBe BodyOptions(…)`: two default engine
instances were never `==`. The fix was making the value types data classes
(`DecompileCache`, `VineflowerDecompiler`), not touching the tests. Rule: any
options/config holder compared in tests must have value equality — default to
`data class` for holders, and treat a hand-rolled class there as a smell.
Learned in session 45 (T-026).

---

### L-077 — `javap` prints no blank line between the class header and the first member `tooling`
Blank-line block splitting swallowed the first member into the `Compiled
from`/class-decl header block (the ctor section vanished; the test caught it
before review). `javap` separates *members* with blanks but not the header
from the first member. Fix: filter `Compiled from` / `{`-ending / `}` lines
first, then blank-split the rest. Sibling gotcha in the same task: `javap
-version` prints to stdout on JDK 26 (stderr on older JDKs) — always read the
merged stream. Learned in session 46 (T-027).

### L-078 — JavaParser hides declarations outside the member list `tooling`
A bytecode-vs-sources member comparison over `TypeDeclaration.members` missed
two declaration sites and flagged every record and annotation type as
mismatched: record components live in the header (`RecordDeclaration`
implements `NodeWithParameters` — read `parameters`, there is no `entries`),
and annotation elements are `AnnotationMemberDeclaration`, not
`MethodDeclaration`. Rule: any source-member enumeration must cover header
parameters and annotation members, or the comparison lies. Caught by the
matched-fixture silence test before review. Learned in session 47 (T-028).

### L-079 — constructors carry hidden leading parameters the source never spells `jvm-spec`
Enum constructors take implicit `(String name, int ordinal)` before the
declared parameters, and inner-class constructors take the enclosing instance
first (`Nesting$Inner(Nesting)` for a source-declared default). A
bytecode-vs-source arity check must strip those prefixes (enum
`(String, int)`, a leading outer-class parameter on nested types) or every
enum/inner type reads as stale. `javap -s` shows the real descriptors, which
is how the shapes were confirmed. Learned in session 47 (T-028).

### L-080 — a regex across serialised JSON rows matches across row boundaries `process`
A `"declaring":"doc.Child".*?"doc":"` assertion meant to count documented
Child rows matched once even with zero such rows: `.*?` spans the `},{`
between rows, so a documented Base row later in the array satisfies it.
Caught by the test itself (expected 0, got 1) before review. Rule:
assert per-row JSON by splitting on `{"ref":` (or by locating the row's own
`"ref":"…#name"` and slicing to the next `}`), never with one regex over
the whole array. Learned in session 48 (T-072).

### L-081 — a second full-corpus pass OOMs the default Gradle test heap `process`
Adding reference-edge extraction (~40 edges/class, 1.13 M rows for the
27.8 k-class JDK) OOMed the `ArtifactIndexerSoakTest` worker: Gradle test
workers default to 512 MB, and edges + member-id map next to the class list
blew past it. Tier-2 tests never noticed (small jars). Rule: any pipeline
addition that multiplies stored rows must re-run the JDK soak, not just
tier 2. Fixes, in order of honesty: release the read lists right after
storing, batch the JDBC writes (safe here — ref rows need no generated ids,
so T-064's no-batching warning does not apply), and size `soakTest` for the
workload (`maxHeapSize = "2g"`, tier 3 is explicitly the heavy tier).
Learned in session 50 (T-029).

### L-082 — ASM tree `InvokeDynamicInsnNode.bsmArgs` is an array, not a list `tooling`
Kotlin reports `for (x in node.bsmArgs ?: emptyList())` as "for-loop range
must have an `iterator()` method", pointing at the loop instead of the type:
`bsmArgs` is `Object[]`. The fix is `?: emptyArray()`. Same family as the
platform-type surprises in L-043: when an ASM tree field misbehaves in a
Kotlin loop, check whether it is a Java array first. Learned in session 50
(T-029).

### L-083 — per-edge targets turn "duplicate" usages rows into information `tooling`
The first `usages` cut rendered one row per edge as `kind fromRef` only, and
the fixture-enum probe printed three byte-identical `read $values()` rows:
the edges differed (RED/YELLOW/GREEN constant reads) but the rendering
dropped the target. Identical adjacent rows always read as a dedupe bug,
even when the data is honest. Rule: any listing whose rows derive from
edges must render the edge target (or enough of it to keep rows distinct) —
here `-> #member` on type-query rows and the full per-edge `target` in
every JSON row. Caught by running the real CLI against the fixture jar
before writing the CLI tests, not by any unit test. Learned in session 51
(T-030).

### L-084 — defaulted data-class fields migrate silently; pin the serialised shape `process`
Adding `srcs` (default `[]`) to `WorkspaceDefinition` kept every positional
construction compiling — a dozen call sites silently meant "no source dirs"
without saying so. The only test that caught the schema change was the TOML
canonical-shape pin (`encode writes the canonical shape`); the resolver and
fixed-point property tests passed unchanged and proved nothing about the new
field until extended. Rule: a defaulted field on a persisted/config type
needs three things in the same commit — the shape pin updated, the
round-trip/defaults examples, and the generative fixed-point widened —
otherwise "green" means "untested". Learned in session 52 (T-031).

### L-085 — printer spacing is a rendering detail; identity compares normalised `process`
The canonical printer emits `", "` between parameters while the reference
parser accepts spaceless `","` — so a callers⟺calls duality test comparing a
hand-written query against a rendered row ref fails on whitespace, not on
semantics (`greet(String,int)` vs `greet(String, int)`). Rule: any test that
asserts method *identity* across the parse/render boundary normalises both
sides (strip `", "` to `","`) instead of hand-writing one spacing and hoping
both ends agree. The dual query itself round-trips either way — only the
string comparison is fragile. Learned in session 54 (T-033).

### L-086 — package refs need a `*` glob; bare dotted names parse as types
The reference parser splits member-less refs by Java naming convention: a
bare `s` — and even a dotted-lowercase `java.lang` — parses as a
`TypeSymbolRef` (the final segment is always the class), so a test expecting
the package-ref exit-3 branch gets exit-1 not-found instead. Only a `*`
anywhere in the ref makes it a `PackageSymbolRef` (e.g. `s.*`). Rule: tests
pinning the package/module rejection branch must use a glob ref, and an
exit-1 on a lowercase dotted query is the parser working as designed, not a
resolution bug. Learned in session 55 (T-034).

### L-087 — `KotlinClassHeader` is deprecated to an error; build `@Metadata` with the `Metadata(...)` helper `kotlin`
`kotlin-metadata-jvm` 2.4.20 deprecates the `KotlinClassHeader` constructor
("Kotlin clients should instantiate Metadata annotation directly"), and this
build promotes deprecations to errors — so the canonical Stack Overflow
snippet for reading `@Metadata` from ASM does not compile here. Rule: build
the annotation with the supported `kotlin.metadata.jvm.Metadata(kind,
metadataVersion, data1, data2, extraString, packageName, extraInt)` helper
and pass it to `KotlinClassMetadata.readLenient`; keep the early-`null` guards
on `k`/`mv`/`d1`/`d2` (absent or mistyped means corrupt, never a throw).
Learned in session 56 (T-035).

### L-088 — `KmClass` has no value equality; compare contents, never carriers `kotlin`
`kotlin-metadata-jvm` model types are mutable holders: two `KmClass` decodes
of the same bytes are `!=`, so a `data class` carrier holding one (here
`KotlinMetadata.kmClass`) silently poisons its own `==` — including the
never-throws/determinism property that pins the reader. Rule: pin declarations
by content (function/property names, flags) in tests, state the caveat in the
carrier's KDoc, and keep it out of golden-pinned shapes. Learned in session 57
(T-076).

### L-089 — never-throw code over metadata/ASM models must distrust every accessor `kotlin`
Three fuzzer catches in one T-077 property suite, all in "can't fail" code:
(1) `KmType.classifier` is `lateinit` — real metadata always sets it, a
hand-built container throws `UninitializedPropertyAccessException` on read;
(2) ASM `Type.getArgumentTypes` parses garbage fine but the later
`.className` throws `IllegalArgumentException`; (3) `Type.getClassName`
throws `AssertionError` — not `Exception` — on hostile inputs, sailing past
`catch (_: Exception)`. Rule: guard `lateinit` model reads with
try/catch-to-degrade, and check hostile descriptors textually instead of via
ASM accessors (the T-077 `isContinuationTail` parses nothing). The
hand-written tests all used well-formed types and caught none of this —
the thousand-case property did. Learned in session 58 (T-077).

### L-090 — `KmProperty.isVar` defaults false on hand-built containers; infer `var` from the setter `kotlin`
A `propertiesFor` unit test built a `KmProperty` with getter+setter signatures
and expected `isVar == true` — it got `false`: the `isVar` flag lives in the
metadata bitfield, and a hand-built container never sets it (like L-088's
equality trap, the model carries more than its constructor shows). Real
compiler metadata sets the flag, but the mapping must not trust it alone.
Rule: fold `var` as `property.isVar || setter != null` (the setter is ground
truth about mutability), and in tests set the flag explicitly when the flag
itself is under test. Learned in session 59 (T-078).

### L-091 — a projection flag must be identity on graphs without views `process`
A `--view jvm` bypass touches every layer the Kotlin view touches (resolver,
matcher, refs, suggestions) — the cheapest proof it changes nothing for
Java is a thousand-case property over the existing view-less generator:
`resolve(target, jvmView=true) shouldBe resolve(target, default)`. It caught
nothing here (the implementation was careful), which is the point: without
the law, "Java byte-identical" rests on a handful of fixture classes, and
the next view-adjacent change has no guardrail. Rule: any bypass/escape-hatch
flag ships with an identity law over the unaffected population, not just
examples of the affected one. Learned in session 60 (T-037).

### L-092 — JavaParser annotation elements are not methods `tooling`
An annotation element (`String value();` inside `@interface Tag`) parses as
`AnnotationMemberDeclaration`, not `MethodDeclaration` — so a name-matcher
written as "methods + fields + enum entries" silently drops every annotation
element, and `body`/`doc` report no source counterpart for a file that plainly
contains the member. `listJavaMembers`-style listings can still see them (they
branch explicitly), which makes the gap extra confusing: the member is listed
but not sliceable. Rule: when matching JavaParser members by kind, always ask
whether `isAnnotationMemberDeclaration` belongs in the set — and keep the
listing branch and the matching branch in sync. Learned in session 61 (T-074,
filed as T-079).

### L-093 — stub the presence class to test an isolated-loader seam `kotlin`
A side-loaded artifact seam (T-038) has three branches — missing, corrupt,
usable — and the usable branch needs the real 55 MB jar, which no hermetic
test may assume. The trick: compile a stub of the presence class
(`KotlinCoreEnvironment`, an empty class in the right package) with the JDK
compiler (`ToolProvider.getSystemJavaCompiler`, skip when null) into a temp
dir and jar it; the seam's load-without-initialise check accepts it, proving
the Available branch end to end in milliseconds. Companion pin: assert the
presence class is *not* on the test classpath, so a future compile dependency
reds the suite instead of silently bloating the fat jar. Learned in session
64 (T-038).

### L-094 — standalone PSI bootstrap is three steps, not one `kotlin`
`KotlinCoreEnvironment.createForProduction` alone fails on
`kotlin-compiler-embeddable` 2.4.20, and each missing step fails differently:
no `idea.home.path` → "Could not find installation home path
(...product-info.json...)"; no application environment → "Extensions storage
is not registered" from `configureProjectEnvironment`; no extension storage
on the `CompilerConfiguration` → the same message from
`getCompilerExtensions`. The working recipe is `idea.home.path` (set once per
JVM when absent) → `getOrCreateApplicationEnvironmentForProduction` (one app
env per JVM, project env per parser) → `setExtensionsStorage` with an empty
`ExtensionStorage` → `createForProduction`. Companion trap: the sidecar set
must include the compiler's runtime jars (stdlib, script-runtime, reflect,
daemon-embeddable, coroutines) as sibling jars on the isolated loader —
`kotlin-compiler-embeddable` bundles none of them, so a lone jar dies with
`NoClassDefFoundError: kotlin/...` *after* the presence check passes.
Diagnose with the deepest cause, not the surface message: reflection wraps
everything in `InvocationTargetException` with a `null` message. Learned in
session 65 (T-039).

### L-095 — KDoc attaches to the following declaration, not the nearest class `kotlin`
A file-header comment above a `typealias` (or any other declaration) between
it and the class is *not* that class's KDoc in PSI terms — `getDocComment()`
returns null and the type correctly reads undocumented, even though a human
reading the file attributes the comment to the class below. A type-KDoc test
that pins a header comment separated from its class by another declaration
reds with `TypeUndocumented` and the implementation is right. Rule: pin type
docs on classes whose doc comment directly precedes their (possibly
annotated) declaration. Learned in session 65 (T-039).

### L-096 — two guards that reject the same input are an unkillable mutant, not defence in depth `process`
A `\uXXXX` reader validated its four characters twice: an explicit
`digits.all { it.isHexDigit() }` and then `toIntOrNull(16)`. Pitest reported six
survivors on `isHexDigit` and no test could kill them — widening the predicate
changed nothing, because the second check rejected the same inputs. The belt was
doing nothing the braces weren't. Fix: one authoritative path
(`digitToIntOrNull(radix = 16)` per character, accumulating), which dropped 8
mutants and raised the package from 81 % to 92 %. Rule for the mutation-gated
`core`: redundant validation reads as thoroughness but measures as a coverage
gap, and the gap is real — nobody can tell you which of the two checks is wrong.
Learned in session 66 (T-040).

### L-097 — PIT's boundary mutator on `c in "chars"` silently drops the set's FIRST character `tooling`
`char in "+-.eE"` compiles to `indexOf(char) >= 0`, so
`ConditionalsBoundaryMutator` produces `> 0` — a mutant that accepts every
member of the set except the one at index 0. It survived a number-scanner test
that already covered `0`, `9`, `1e3` and `0.5`, because none of them contained a
`+`. Rule: a char-set membership test needs a case exercising the set's *first*
element specifically (here, a JSON exponent written `1e+3`); ordering the
literal so its first character is one you already test is the cheaper habit.
Learned in session 66 (T-040).

### L-098 — `Socket.socket()` does not speak AF_UNIX `tooling`
Every unix-socket probe in the T-041 suite returned `null` — connects,
writes and reads all threw — because `SocketChannel.socket()` (and its
streams/soTimeout) only supports INET: for `StandardProtocolFamily.UNIX`
channels it throws `UnsupportedOperationException`. The failure hid inside
the probe's never-throws `catch → null`, so all 13 tests failed identically
with no stack trace until one was reproduced outside the catch. Rule: talk
to unix sockets with `ByteBuffer` reads/writes only (a `Selector` read
timeout on the client, blocking reads on the server's per-connection
thread), and when a never-throws wrapper fails everywhere at once, suspect
the wrapper's shared primitive before the logic under test. Learned in
session 67 (T-041).

### L-099 — nullable params need a presence check, not `?:`
`engine` (absent = ladder default) and `lines` (absent = whole file) both
parse to a nullable type where `null` also means "invalid" — so `parse() ?:
return failure()` rejects the common no-flag case with a usage error. The
first version additionally hid the bug behind an `optionalX()` helper that
returned the same conflated null. Rule: for any param whose valid value can
be null, check presence (`has("engine")`) at the call site and only parse
when present. Learned in session 68 (T-082).
