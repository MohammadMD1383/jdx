## D-051 — Kotlin property folding + default-arg annotation semantics (T-078) · proposed-by-implementer

**Context:** T-036 maps JVM members back onto Kotlin declarations
(PROPOSAL.md §9.3 step 7, §12.1). Its third slice folds the two remaining
JVM-projection lies over the T-076 carrier: properties (`getX`/`setX` → `val`/`var`)
and default arguments (`foo$default` stubs → `= ...` markers). The fixture proves
each one (`KotlinData` getters/setters + `copy` defaults, `withDefault` second-param
default, `UserIdBox.getId` → `val id`, `Sealed$Sub.getX` → `val x`).

**Decisions:**
1. **Properties are a fourth row kind.** `MemberKind.PROPERTY` (`property`/`properties`,
   after `FIELD` so existing ordinals stay stable) with `MemberCounts.properties`
   (default `0`; JSON/text include it only when > 0, so Java goldens stay byte-identical).
   Rows render Java-style with a `val`/`var` keyword:
   `property public final val java.lang.String name`. The access rides the view
   (the getter's JVM access, populated by `index`); the type is the metadata
   `KmType` via the T-077 renderer, falling back to the getter's JVM return
   (type variables erase — keep the JVM text, never a bare `Object`).
2. **Accessors and backing fields hide unless `--include-synthetic`.**
   `ClassInfo` gains `kotlinProperties` (name → view), `kotlinHiddenMethods`
   (JVM keys of folded getters/setters) and `kotlinHiddenFields` (backing-field
   names, via `fieldSignature`). `MemberResolver` skips hidden members when
   `includeSynthetic` is false and synthesises one `ResolvedProperty` per
   declaration (nearer wins by name, like fields). `--include-synthetic` shows
   both (JVM truth hatch, T-037 precursor).
3. **Default args annotate, overloads stay.** `KotlinMethodView` gains
   `defaultArgIndices` (Kotlin positions from `KmValueParameter.declaresDefaultValue`);
   renderers suffix those params with `= ...` (`withDefault(int first, String second = ...)`).
   `$default` stubs are already synthetic-hidden; `@JvmOverloads` overloads
   (`withDefault(int)`) stay — they are real Java API, and folding them would
   hide callable overloads.
4. **Matching accepts property names; bodies/docs stay JVM.**
   `matchBytecodeMembers` returns a `Property` match for bare `Owner#name`
   (JVM exact first, property alias second); `signature` renders it;
   did-you-mean suggests property names; `--kind property` filters to them.
   `body`/`doc` on a property name exit 1 naming T-039 (Kotlin PSI bodies/KDoc own
   them — a getter slice would mislead); `callers`/`calls`/`usages` stay
   JVM-spelled (use `getX`).
5. **The store drops the new views; the command differential still skips Kotlin.**
   No `ktmeta` blob writer and no migration (D-049 §3/D-050 §4 stand):
   `ArtifactIndexerTest`/`IndexStoreTest` pin the drop explicitly. File facades
   stay JVM (no carrier); `--view jvm` stays parked (T-037).

**Status:** proposed-by-implementer. Decided 2026-09-22, session 59 (T-078).

## D-052 — `--view jvm` projection semantics (T-037) · proposed-by-implementer

**Context:** T-036 maps JVM members back onto Kotlin declarations
(PROPOSAL.md §9.3 step 7, §12.1). Its last slice is the escape hatch the
proposal promises: `--view jvm` forcing the raw JVM projection for agents
that genuinely need the JVM truth (calling Kotlin from Java, reading a
stack trace). `members`/`outline`/`signature` gain `--view kotlin|jvm`
(default `kotlin`); the fixture proves each projection (`KotlinMembers`
JVM names + `Continuation` + mangled `internal` + unfolded accessors,
`KotlinData` getters + backing field).

**Decisions:**
1. **A view flag, not a mode.** `JdxService.MemberView` (`KOTLIN`/`JVM`,
   `flag` strings mirroring `KindFilter`) rides `MemberFilters.view` and
   `SignatureOptions.view` (both default `KOTLIN`), so the thin-adapter
   `MemberQuery`/`SignatureQuery` arities stay stable (D-004) and every other
   command keeps its signature. The CLI maps it with `viewOf` (unknown →
   `KOTLIN`; Clikt `choice()` rejects anything else with exit 3).
2. **JVM view ignores every Kotlin view, end to end.** `MemberResolver`
   gains `MemberResolutionOptions.jvmView` (default `false`): folded
   accessors/backing fields stay visible as plain members, no `kotlinView`
   attaches, no `ResolvedProperty` synthesises — while real synthetics still
   honour `includeSynthetic`. `matchBytecodeMembers` matches JVM-exact only
   (no property alias, empty view map — true `javap` parity); refs spell JVM
   names; did-you-mean pools JVM names only.
3. **Kotlin spellings in JVM view are misses, not aliases.** A Kotlin
   declaration name (`originalName`) or property name under `--view jvm`
   exits 1 with JVM suggestions — except where the JVM truth answers anyway:
   `KotlinData#name` names the private backing field `javap` shows, so it
   renders the field line (exit 0). `body`/`doc`/`usages`/`hierarchy`/
   `callers`/`calls`/`samples` gain no flag (already JVM-spelled per D-051);
   `show` has no members to project.
4. **The command differential re-includes Kotlin via JVM view.**
   `ServiceDifferential.compare` queries Kotlin classes with the JVM
   projection instead of skipping them (`Comparison.Compared.jvmView` marks
   the path; the tier-2 suite asserts it fired). Tier-3 soak inherits it:
   112 classes compared with zero Kotlin mismatches, the only failure the
   known pre-existing `JrtDirectoryStream` drift.
5. **Goldens pin the projection, not the default.** A dedicated
   `KotlinJvmViewGoldenTest` (`golden/jvm-view/`) pins members + signature
   for the Kotlin fixtures under JVM view; the Kotlin-view goldens are
   untouched. Java output is byte-identical across views (pinned by test).

**Status:** proposed-by-implementer. Decided 2026-09-22, session 60 (T-037).

## D-053 — `usages` graph-enrichment semantics (T-075) · proposed-by-implementer

**Context:** T-075 teaches `usages` the three parked `--kind` values
(`new|throw|annotation`) and settles `--context`. The T-029 edge vocabulary
is closed at four kinds (D-042) with no `line` data in v1 (D-042 §4), and the
`ref` table has no descriptor-independent throw/annotation columns — a new
edge vocabulary would need an extractor change plus a store migration for no
indexed reader (queries are still live-roots scans, D-043).

**Decisions:**
1. **`new` is a filtered view, not a new edge.** `--kind new` shows
   `METHOD_CALL` edges to `<init>` only, rendered with the kind word `new`.
   Under `all` constructors keep their `call` (+ `NEW` instruction `ref`)
   rows, so nothing double-counts.
2. **`throw` reads `throws` declarations.** `--kind throw` on a type shows
   every method/ctor whose `throws` declares it (ClassInfo metadata over the
   same live-roots scan). `ATHROW` throw *sites* are not resolved in v1 —
   attributing a stack-polymorphic `athrow` to a type needs data-flow the
   extractor deliberately skips; the declaration is the honest, exact answer.
3. **`annotation` reads annotation uses.** `--kind annotation` on a type
   shows annotated classes (bare binary from-ref) and annotated members
   (`Owner#member(params)`). Both live in ClassInfo already; no ASM change.
4. **Metadata kinds are type-level.** A member ref with `throw`/`annotation`
   scans nothing and reports no usages (exit 1, the D-043 §5 convention) —
   a method has no throwers and an annotation use is found via its type.
   Source-dir textual mentions stay `ref`-only (D-044): the new kinds show
   bytecode-backed rows alone.
5. **`--context` stays a `samples` redirect.** Inline snippets would
   duplicate `jdx samples` per edge row and blow the token budget the
   truncation footer protects; the exit-3 message names the command.
6. **No store change.** All three kinds ride the live-roots scan (D-043
   precedent); indexed acceleration still lands with the daemon/`jdx index`
   work, which will persist whatever vocabulary it needs then.

**Status:** proposed-by-implementer. Decided 2026-09-22, session 63 (T-075).
