## D-051 — Kotlin property folding + default-arg annotation semantics (T-078) · proposed-by-implementer

**Context:** T-036 maps JVM members back onto Kotlin declarations
(PROPOSAL.md §9.3 step 7, §12.1). Its third slice folds the two remaining
JVM-projection lies over the T-076 carrier: properties (`getX`/`setX` → `val`/`var`)
and default arguments (`foo$default` stubs → `= ...` markers). The fixture proves
each one (`KotlinData` getters/setters + `copy` defaults, `withDefault` second-param
default, `UserIdBox.getId` → `val id`, `Sealed$Sub.getX` → `val x`).

**Decisions:**
1. **Properties are a fourth row kind.** `MemberKind.PROPERTY` (`property`/`properties`,
   after `FIELD` so existing ordinals stay stable) with `MemberCounts.properties`
   (default `0`; JSON/text include it only when > 0, so Java goldens stay byte-identical).
   Rows render Java-style with a `val`/`var` keyword:
   `property public final val java.lang.String name`. The access rides the view
   (the getter's JVM access, populated by `index`); the type is the metadata
   `KmType` via the T-077 renderer, falling back to the getter's JVM return
   (type variables erase — keep the JVM text, never a bare `Object`).
2. **Accessors and backing fields hide unless `--include-synthetic`.**
   `ClassInfo` gains `kotlinProperties` (name → view), `kotlinHiddenMethods`
   (JVM keys of folded getters/setters) and `kotlinHiddenFields` (backing-field
   names, via `fieldSignature`). `MemberResolver` skips hidden members when
   `includeSynthetic` is false and synthesises one `ResolvedProperty` per
   declaration (nearer wins by name, like fields). `--include-synthetic` shows
   both (JVM truth hatch, T-037 precursor).
3. **Default args annotate, overloads stay.** `KotlinMethodView` gains
   `defaultArgIndices` (Kotlin positions from `KmValueParameter.declaresDefaultValue`);
   renderers suffix those params with `= ...` (`withDefault(int first, String second = ...)`).
   `$default` stubs are already synthetic-hidden; `@JvmOverloads` overloads
   (`withDefault(int)`) stay — they are real Java API, and folding them would
   hide callable overloads.
4. **Matching accepts property names; bodies/docs stay JVM.**
   `matchBytecodeMembers` returns a `Property` match for bare `Owner#name`
   (JVM exact first, property alias second); `signature` renders it;
   did-you-mean suggests property names; `--kind property` filters to them.
   `body`/`doc` on a property name exit 1 naming T-039 (Kotlin PSI bodies/KDoc own
   them — a getter slice would mislead); `callers`/`calls`/`usages` stay
   JVM-spelled (use `getX`).
5. **The store drops the new views; the command differential still skips Kotlin.**
   No `ktmeta` blob writer and no migration (D-049 §3/D-050 §4 stand):
   `ArtifactIndexerTest`/`IndexStoreTest` pin the drop explicitly. File facades
   stay JVM (no carrier); `--view jvm` stays parked (T-037).

**Status:** proposed-by-implementer. Decided 2026-09-22, session 59 (T-078).

## D-052 — `--view jvm` projection semantics (T-037) · proposed-by-implementer

**Context:** T-036 maps JVM members back onto Kotlin declarations
(PROPOSAL.md §9.3 step 7, §12.1). Its last slice is the escape hatch the
proposal promises: `--view jvm` forcing the raw JVM projection for agents
that genuinely need the JVM truth (calling Kotlin from Java, reading a
stack trace). `members`/`outline`/`signature` gain `--view kotlin|jvm`
(default `kotlin`); the fixture proves each projection (`KotlinMembers`
JVM names + `Continuation` + mangled `internal` + unfolded accessors,
`KotlinData` getters + backing field).

**Decisions:**
1. **A view flag, not a mode.** `JdxService.MemberView` (`KOTLIN`/`JVM`,
   `flag` strings mirroring `KindFilter`) rides `MemberFilters.view` and
   `SignatureOptions.view` (both default `KOTLIN`), so the thin-adapter
   `MemberQuery`/`SignatureQuery` arities stay stable (D-004) and every other
   command keeps its signature. The CLI maps it with `viewOf` (unknown →
   `KOTLIN`; Clikt `choice()` rejects anything else with exit 3).
2. **JVM view ignores every Kotlin view, end to end.** `MemberResolver`
   gains `MemberResolutionOptions.jvmView` (default `false`): folded
   accessors/backing fields stay visible as plain members, no `kotlinView`
   attaches, no `ResolvedProperty` synthesises — while real synthetics still
   honour `includeSynthetic`. `matchBytecodeMembers` matches JVM-exact only
   (no property alias, empty view map — true `javap` parity); refs spell JVM
   names; did-you-mean pools JVM names only.
3. **Kotlin spellings in JVM view are misses, not aliases.** A Kotlin
   declaration name (`originalName`) or property name under `--view jvm`
   exits 1 with JVM suggestions — except where the JVM truth answers anyway:
   `KotlinData#name` names the private backing field `javap` shows, so it
   renders the field line (exit 0). `body`/`doc`/`usages`/`hierarchy`/
   `callers`/`calls`/`samples` gain no flag (already JVM-spelled per D-051);
   `show` has no members to project.
4. **The command differential re-includes Kotlin via JVM view.**
   `ServiceDifferential.compare` queries Kotlin classes with the JVM
   projection instead of skipping them (`Comparison.Compared.jvmView` marks
   the path; the tier-2 suite asserts it fired). Tier-3 soak inherits it:
   112 classes compared with zero Kotlin mismatches, the only failure the
   known pre-existing `JrtDirectoryStream` drift.
5. **Goldens pin the projection, not the default.** A dedicated
   `KotlinJvmViewGoldenTest` (`golden/jvm-view/`) pins members + signature
   for the Kotlin fixtures under JVM view; the Kotlin-view goldens are
   untouched. Java output is byte-identical across views (pinned by test).

**Status:** proposed-by-implementer. Decided 2026-09-22, session 60 (T-037).

## D-053 — `usages` graph-enrichment semantics (T-075) · proposed-by-implementer

**Context:** T-075 teaches `usages` the three parked `--kind` values
(`new|throw|annotation`) and settles `--context`. The T-029 edge vocabulary
is closed at four kinds (D-042) with no `line` data in v1 (D-042 §4), and the
`ref` table has no descriptor-independent throw/annotation columns — a new
edge vocabulary would need an extractor change plus a store migration for no
indexed reader (queries are still live-roots scans, D-043).

**Decisions:**
1. **`new` is a filtered view, not a new edge.** `--kind new` shows
   `METHOD_CALL` edges to `<init>` only, rendered with the kind word `new`.
   Under `all` constructors keep their `call` (+ `NEW` instruction `ref`)
   rows, so nothing double-counts.
2. **`throw` reads `throws` declarations.** `--kind throw` on a type shows
   every method/ctor whose `throws` declares it (ClassInfo metadata over the
   same live-roots scan). `ATHROW` throw *sites* are not resolved in v1 —
   attributing a stack-polymorphic `athrow` to a type needs data-flow the
   extractor deliberately skips; the declaration is the honest, exact answer.
3. **`annotation` reads annotation uses.** `--kind annotation` on a type
   shows annotated classes (bare binary from-ref) and annotated members
   (`Owner#member(params)`). Both live in ClassInfo already; no ASM change.
4. **Metadata kinds are type-level.** A member ref with `throw`/`annotation`
   scans nothing and reports no usages (exit 1, the D-043 §5 convention) —
   a method has no throwers and an annotation use is found via its type.
   Source-dir textual mentions stay `ref`-only (D-044): the new kinds show
   bytecode-backed rows alone.
5. **`--context` stays a `samples` redirect.** Inline snippets would
   duplicate `jdx samples` per edge row and blow the token budget the
   truncation footer protects; the exit-3 message names the command.
6. **No store change.** All three kinds ride the live-roots scan (D-043
   precedent); indexed acceleration still lands with the daemon/`jdx index`
   work, which will persist whatever vocabulary it needs then.

**Status:** proposed-by-implementer. Decided 2026-09-22, session 63 (T-075).

## D-054 — Kotlin PSI side-load seam: versioned sidecar + presence-vs-usability split (T-038) · proposed-by-implementer

**Context:** D-008 mandates full `kotlin-compiler-embeddable` PSI behind five
mitigations (interface boundary, lazy isolated loading, side-loaded jar, once
per daemon, `doctor` reporting). T-038 builds the loading half before T-039
builds PSI queries on it, so the seam must already prove isolation without
paying parse costs or bloating the fat jar.

**Decisions:**
1. **Versioned sidecar path.** `~/.cache/jdx/kotlin/
   kotlin-compiler-embeddable-<version>.jar`; the version is a `const` in
   `sources` mirroring `libs.versions.toml#kotlinCompiler` (change both
   together — the catalog comment points back). A versioned file (not a
   directory) means an upgrade never talks to a stale jar.
2. **Presence vs usability are different checks.** `probeKotlinToolchain`
   (cheap, cold-path safe) reports regular-file + non-empty only; `doctor
   kotlin` renders that (OK vs WARN). Real usability — isolated loader opens
   *and* the presence class loads — is verified at open time by
   `openKotlinParser`, whose failure is an unavailable value with the cause,
   never a throw. `doctor` saying OK for a corrupt jar is accepted (it is a
   presence row, like `index`); the use path still degrades honestly.
3. **Isolated loader, platform parent, load-without-initialise.**
   `URLClassLoader(arrayOf(jar), getPlatformClassLoader())` — never the app
   loader — and `Class.forName(name, false, loader)` for
   `KotlinCoreEnvironment`: proves the jar is a real compiler sidecar without
   the ~1 s PSI init, which T-039 pays once per daemon lifetime. The parser
   holds the loader and closes it; close never throws.
4. **The no-compile-dependency premise is test-pinned.** A test asserts the
   presence class is *not* loadable from the test classpath: adding the
   compiler as a real dependency reds the suite before the fat jar can bloat.
   Compiler names appear only as string literals outside reflective use.

**Status:** proposed-by-implementer. Decided 2026-09-22, session 64 (T-038).

## D-055 — Kotlin bodies/KDoc over the side-loaded PSI seam (T-039) · proposed-by-implementer

**Context:** T-038 built the D-008 loading half (versioned sidecar path,
isolated loader, `doctor` row); T-039 builds the PSI queries on it, closing
M5. The compiler must parse `.kt` text with real PSI ranges, reached only by
reflection (no compile dependency, never in the fat jar).

**Decisions:**
1. **Standalone bootstrap is three steps, all reflective.** `KotlinCoreEnvironment.createForProduction`
   alone fails on 2.4.20 — first `idea.home.path` (the platform `PathManager`
   needs it; set once per JVM when absent, pointing at an `idea-home` dir
   under the sidecar dir), then `getOrCreateApplicationEnvironmentForProduction`
   (the application environment is one per JVM, shared across parsers), then an
   empty `ExtensionStorage` registered via `setExtensionsStorage` (the 2.x
   project bootstrap queries compiler extensions off the configuration).
   Each miss was found empirically against the real jar and is named in the
   degradation detail (deepest-cause label, since reflection wraps everything
   in `InvocationTargetException` with a `null` message).
2. **The sidecar is a set, not a file.** `kotlin-compiler-embeddable` does not
   bundle the stdlib (nor script/reflect/daemon/coroutines runtimes), so a
   lone compiler jar cannot initialise. The loader reads the sidecar plus
   every `.jar` sibling in its directory (sorted, deterministic); the T-038
   versioned-file probe stays the presence signal, and a lone jar reads as a
   presence-OK / use-degrades split (D-054 §2). The fetch task (T-080)
   installs the set together with checksums.
3. **One parser per command, env init lazy.** Opening is milliseconds
   (classloader + presence check); the ~1 s PSI init happens on the first
   parse. `body`/`doc` open one parser for the whole command (shared across
   lookup spellings, supertype walks and `--with-doc`); `source --around`
   and whole-file `.kt` open their own; best-effort paths (listing
   `--with-doc`, samples snippets) share one ambient parser per command.
   No auto-fetch: a missing sidecar degrades (body/source→ladder,
   doc→install hint), per the T-019 no-surprise-network ethos — the hint is
   `~`-relative (`kotlinMissingHint`), never an absolute home path (§2.5).
4. **Seam results reuse the Java types.** `findKotlinBodies`/`findKotlinMemberDocs`/
   `findKotlinTypeDoc`/`listKotlinMembers` return `JavaBodyResult`/`JavaDocResult`/
   `JavaMemberList` (+ a `ParserUnavailable` case each), so renderers and
   provenance stay shared; a property slices as `FIELD`, a ctor as
   `CONSTRUCTOR`. Callers map Java `NoSource`/`NotJava` onto the Kotlin
   attempt, except the decompiled loops (unreachable → `memberNotFound`,
   L-073 style). `NoSource` with no `.kt` evidence anywhere stays `NoSource`
   (unconfirmed text mentions only route to degradation when PSI is unusable).
5. **Matching is Kotlin-aware, structure stays bytecode-first (D-009).**
   Overload ambiguity is still decided from bytecode; the seam only slices.
   Source matching accepts `@JvmName`/unmangled-`internal`/property aliases
   (passed as `aka` from the bytecode match), JVM-spelled `suspend`
   (trailing `Continuation`), extension receivers (leading param),
   omitted trailing defaults, and `Int`/`Any?`→JVM key normalisation.
   Companion members answer for their class; `<init>` matches explicit
   primary + secondaries; KDoc the PSI range includes is trimmed from bodies.
6. **Deferred, documented.** Whole-file `source` serves `.kt` verbatim (no
   parse needed). `SOURCES_VERSION_MISMATCH` does not fire for Kotlin pairs
   (compiler-generated members — data `componentN`/`copy`, value-class
   `-impl`s, `@JvmOverloads` — would false-positive a JVM-name pairing;
   needs `@Metadata`-aware pairing, T-081). Facade file-docs, Kotlin enum
   entries with bodies, and parameterised extension queries stay minimal.

**Status:** proposed-by-implementer. Decided 2026-09-22, session 65 (T-039).

## D-056 — `JdxService` RPC v1 wire contract (T-040) · proposed-by-implementer

**Context:** M6 puts four servers in front of one service (daemon T-041, CLI
client T-042, MCP T-043, HTTP T-044, `batch` T-045). PROPOSAL.md §14 described
the four interfaces but never the bytes they share, and T-046 has to prove they
are byte-identical. T-040 fixes the contract first, in `core`, before any
transport exists. Decisions taken while writing `core/.../rpc/RpcProtocol.kt`:

1. **Requests are newline-delimited JSON; responses are the existing envelope.**
   There is no second response shape to keep in sync — a response is exactly
   `ServiceOutcome.toJson(command)` (§8.2). Parity (T-046) is therefore
   structural, not a pile of per-adapter goldens.
2. **One request shape, always.** Fixed key order (`jdx`, `command`, `query`,
   `params`), `params` sorted by key and emitted even when empty. Adapters never
   branch on a field's presence, and equal requests are byte-equal — the same
   determinism rule the renderers already obey (CLAUDE.md §2.5).
3. **Param values are text.** `"true"`, `"50"` — the spelling the CLI's own flags
   use, so one value has one form across all four adapters. Typed clients (MCP
   integer/boolean schemas, HTTP query strings) legitimately send JSON numbers
   and booleans, so `decode` accepts those and canonicalises them to their text.
   Arrays, objects and `null` are refused: they have no single text meaning.
4. **The wire is read-only in v1.** `ws` and `cache` are absent from `RpcCommand`
   on purpose. A daemon serves several clients at once; letting one of them
   repoint the workspace would silently change what the others are answering
   about. They stay CLI-local until a task argues otherwise.
5. **Generous where safe, strict where a guess would be dangerous** (CLAUDE.md
   §6 applied to the wire, not just to symbol refs). Accepted: surrounding
   whitespace, trailing `\r\n`, absent `jdx`/`query`/`params`, unknown top-level
   keys (forward compatibility, the same reasoning as the envelope's reserved
   fields in D-027). Refused with `null`, never a best guess: unknown command,
   a version other than `RPC_VERSION`, a wrongly-typed field, a structured or
   null param value, a truncated object, trailing content after it.
6. **`decode` never throws, and nesting is bounded at 32.** A daemon parses
   whatever a socket hands it, so the reader returns `null` rather than raising,
   and refuses depth beyond `MAX_DEPTH` instead of recursing into a stack
   overflow. This is a hand-rolled parser because `core` takes no dependencies
   (D-028) — it is private to the file and must not grow into a general-purpose
   JSON library.
7. **`RpcCommand` carries `requiresQuery`.** `ls`/`tree` default their glob to
   `*` and `version`/`doctor`/`health` take no subject. The flag lives in the
   enum so all four adapters validate identically instead of each re-deriving it
   (CONTRIBUTING.md: no logic in adapters). The codec itself does *not* enforce
   it — `JdxService` already answers bad input with exit 3, and duplicating that
   would create a second source of truth.

**Consequences:** renaming a `wire` value is a breaking change (MCP derives
`jdx_<wire>` tool names, HTTP `/v1/<wire>` paths). `RPC_VERSION` mirrors
`ENVELOPE_VERSION`; bumping either is a wire break, which is also why T-041's
socket path is version-stamped.

**Status:** proposed-by-implementer. Decided 2026-09-22, session 66 (T-040).

## D-057 — daemon transport + lifecycle semantics (T-041) · proposed-by-implementer

**Context:** T-041 owns the daemon transport (PROPOSAL.md §14.3): the socket,
the framing loop, lifecycle (`start|stop|status|restart`) and idle shutdown.
Full `JdxService` query dispatch does not fit the same sitting, so it is
split out as T-082; the T-041 daemon answers `health`/`version` internally
and refuses read queries with an honest exit-6 envelope naming T-082.
Decisions taken while writing `server/.../DaemonPaths.kt`,
`DaemonIdle.kt`, `DaemonServer.kt` and `cli/.../commands/DaemonCommand.kt`:

1. **Socket path is `$XDG_RUNTIME_DIR/jdx/<16-hex-sha256-of-workspace>-v<rpc-version>.sock`.**
   Hashed (not raw) workspace names cannot escape the socket directory, and
   the version stamp in the file name means an upgraded `jdx` looks for a
   different socket instead of half-understanding a stale daemon. Pid and log
   files are siblings (`.pid`/`.log`). No `XDG_RUNTIME_DIR` → exit 3, never a
   fallback Hamburied in `/tmp`: `doctor` already reports that state.
2. **Raw channel IO, never `Socket.socket()`.** `java.net.Socket` does not
   speak AF_UNIX — every probe returned `null` until the transport moved to
   `ByteBuffer` reads/writes plus a `Selector` read timeout on the client
   (L-098). Server side stays blocking (one virtual thread per connection);
   only the probe needs the timeout.
3. **Strict 1:1 line mapping.** Every input line gets exactly one envelope
   line — including blank and malformed lines, which get an exit-6 envelope
   (`command:"unknown"`) rather than a dropped connection. Pipelined clients
   can therefore always pair responses to requests.
4. **Idle shutdown is a reset-per-request single-shot task.**
   `ScheduledExecutorService`, default 5 min, `--idle 0` disables
   (`Duration.ZERO` preserved through parsing so "disabled" and "garbage"
   stay distinct). The task calls the same idempotent `stop()` everything
   else calls, so idle death cleans socket + pid files like `stop` does.
5. **`daemon run` is the spawn target; `start` is its supervisor.**
   `start` execs `java.home`'s `java -cp <current-classpath>
   dev.jdx.cli.JdxCliKt daemon run …` detached (log sibling captures output),
   then polls `health` for 5 s. `start` on a live daemon exits 0
   (idempotent); `stop` kills via the pid file and sweeps stale files;
   `status` prints uptime/workspace/memory/indexed-artifacts/query-count with
   a `--json` envelope. Exit codes follow D-015 (1 = not running, 3 = usage,
   6 = spawn/IO).
6. **`cli` depends on `:server` for transport only.** The socket server,
   probe, paths and idle parsing live in `:server`; the `daemon` Clikt group
   only parses flags and prints (D-004 intact). The daemon's `health`
   `result` shape is deliberately small and daemon-specific — T-046 parity
   covers the 17 read queries, not the liveness probe.

**Status:** proposed-by-implementer. Decided 2026-09-23, session 67 (T-041).

## D-058 — daemon query-dispatch semantics (T-082) · proposed-by-implementer

**Context:** T-082 wires the T-041 transport to `JdxService`: all 17 read
`RpcCommand`s dispatch to the same service methods the one-shot CLI calls, and
responses are `ServiceOutcome.toJson(wire)` verbatim, so warm answers are
byte-identical to cold ones (the T-046 parity proof stays structural, D-056
§1). Decisions taken while writing `index/.../service/RpcDispatch.kt`,
`server/.../DaemonDispatch.kt` and the `daemon run` wiring:

1. **Param contract is flag names as text.** Param keys are the CLI long-flag
   names without dashes (`kind`, `limit`, `includeSynthetic`), values are flag
   values as text (`"true"`, `"50"` — the T-040 spelling), absent means the
   CLI default. The T-042 client therefore forwards flags verbatim. Unknown
   enums and unparseable integers are exit-3 usage errors naming the param —
   never a guess, never a throw. Full per-command table in the `dispatch`
   KDoc; T-043/T-044 build on the same contract.
2. **Dispatch lives in `:index`, next to the service.** Param parsing is
   behaviour, so it sits in `RpcDispatch.kt` (same package as `JdxService`)
   as `JdxService.dispatch` / `JdxService.daemonRoots`; `:server` only
   resolves roots and serialises (D-004 intact — hence the new
   `:server`→`:index` dependency, mirroring `:cli`→`:index`).
3. **Daemon roots are `-w <name>` semantics, per request.** The daemon serves
   exactly its named workspace; a missing workspace is exit 4 (like one-shot
   `-w`), an unresolvable stored coordinate exit 5 — never a silent fallback
   to other roots. Resolution runs per request so `ws create` mid-life is
   picked up; stored `--repo` mirrors are inert (the daemon never fetches,
   `allowFetch = false`, so no network from a background process).
4. **`doctor` is refused, exit 6.** It reports the caller's machine
   environment and `DoctorService` lives in `:cli`, which `:server` cannot
   depend on (`:cli` already depends on `:server`) — so the handler names
   `jdx doctor` instead of guessing. `health`/`version` stay on the T-041
   internals; `implementors` dispatches through `hierarchy(up=false,
   down=true)` with the `implementors` wire name preserved in the envelope.
5. **`indexedArtifacts` stays 0.** No persistent index lands here (live roots
   first, D-043 precedent) — 0 is the honest count of indexed artifacts, and
   the `open-items.md` caveat now says so instead of "until T-082".

**Status:** proposed-by-implementer. Decided 2026-09-23, session 68 (T-082).

## D-059 — transparent CLI daemon client semantics (T-042) · proposed-by-implementer

**Context:** T-042 puts the one-shot CLI in front of the T-041 transport +
T-082 dispatch: forward the T-040 request when a daemon answers, else run
in-process (PROPOSAL.md §14.1). Decisions taken while writing
`cli/.../DaemonClient.kt` and the `--no-daemon` plumbing across all 17 read
commands:

1. **Warm serves `--json` only in v1; text stays in-process.** The wire
   response is the `--json` envelope verbatim (D-056) and there is no text
   wire, so serving warm text would mean rebuilding 17 renderers from JSON.
   The daemon's audience is programmatic (`--json`/MCP/HTTP); text stays
   correct, just cold. A text-wire or JSON→Outcome parser is the follow-up,
   not this slice.
2. **Forward only when the daemon would answer about the same roots.** Any
   explicit root override (`--jars`, `--coord`, `--repo`, `--fetch`,
   `--src`, `--no-jdk`) or an auto-discovered (unnamed) workspace bypasses
   the daemon: it serves its stored workspace only (D-058 §3), so anything
   else would answer about different roots. The warm attempt runs before root
   resolution, so a warm hit also skips all workspace/Maven IO.
3. **Usage errors fail fast locally, before any socket IO.** Flag validation
   runs first; the daemon would answer exit 3 too, but its messages name
   params where the CLI names flags.
4. **Pairing is the transport's job, not the envelope's query.** Warm exit
   codes come from the envelope (`ok:true` → 0, else `error.code`), gated on
   the `command` echo and the v1 marker — but NOT on the `query` echo, which
   the service normalises (`ls`/`tree` answer an empty query as `"*"`, L-100).
   The strict 1:1 line mapping (D-057 §3) already pairs responses to requests.
5. **`doctor`/`version` never leave the process.** `doctor` reports the
   caller's environment (and the daemon refuses it, D-058 §4); `version` is
   a build constant. Only the 17 read commands attempt warm.
6. **`--no-daemon` lives on the root and on every read command**, mirroring
   the `--json` dual position (D-027): `jdx --no-daemon members ...` and
   `jdx members --no-daemon ...` are equivalent.

**Status:** proposed-by-implementer. Decided 2026-09-23, session 69 (T-042).

## D-060 — MCP stdio server semantics (T-043) · proposed-by-implementer

**Context:** T-043 exposes every T-040 command as a typed `jdx_<wire>` MCP
tool over stdio (PROPOSAL.md §14.2), with schemas generated from the same
command metadata the CLI uses. Decisions taken while writing
`mcp/.../McpTools.kt`, `McpSession.kt`, `McpServer.kt` and `cli/.../McpCommand.kt`:

1. **One table is the metadata; schema and wire read it.** `ALL_MCP_TOOLS`
   declares each command once (description + typed params); `inputSchema()`
   builds the SDK `ToolSchema` from those rows and `requestFor()` builds the
   `RpcRequest` from the same rows. Param names are the D-058 wire spellings,
   so MCP/daemon/CLI cannot drift — and the tier-2 suite proves it by
   comparing each tool's answer against the hand-written equivalent request.
2. **The session is a per-session daemon over one stored workspace.**
   `jdx mcp [-w name]` (default `default`) resolves roots per call through
   `JdxService.daemonRoots` — the same seam the socket daemon uses — so `ws
   create` while the server runs is picked up, and a missing workspace reads
   as exit 4 naming the fix. No auto-discovery, no explicit `--jars`: the
   daemon has neither, and the one-shot CLI keeps both. A per-tool
   `workspace` argument overrides the server default for that call.
3. **Tool results are the `--json` envelope verbatim.** Text content carries
   the envelope bytes (the T-046 parity shape), structured content carries
   the parsed envelope, and `isError` carries the exit-code branch
   (`ok:false` reads as `true`) so agents branch without parsing prose.
4. **`version`/`health` are internal in the daemon's envelope shapes**
   (same key order, so clients read either server alike; `indexedArtifacts`
   stays 0 — live roots, no persistent index, the D-043 precedent).
   `doctor` is refused with exit 6 naming `jdx doctor`: it reports the
   machine's environment and `DoctorService` lives in `:cli`, which `:mcp`
   cannot depend on (`:cli` depends on `:mcp`).
5. **Stdio discipline: stdout is the protocol.** kotlin-logging's startup
   banner goes to stdout, so the server silences it before creating the
   transport (L-101); slf4j has no binding in the fat jar and stays silent.
   The server returns on stdin EOF (transport `onClose`, bounded close) and
   the CLI entry exits 0 after serving instead of hanging on
   `awaitCancellation` (L-102) — a lingering JVM per disconnected client
   would be a leak.
6. **`:cli` never names SDK types.** `serveMcpStdioBlocking(session,
   version)` is the one blocking entry; `McpCommand` parses `-w` and calls
   it (new `:cli`→`:mcp` dep, mirroring the `:cli`→`:server` one, D-004
   intact).

**Status:** proposed-by-implementer. Decided 2026-09-23, session 70 (T-043).

## D-061 — HTTP/JSON server semantics (T-044) · proposed-by-implementer

**Context:** T-044 serves every T-040 command over HTTP on the JDK builtin
`com.sun.net.httpserver` (PROPOSAL.md §14.4, zero dependencies), as
`jdx serve [-w name] [--port 7070] [--bind 127.0.0.1]`. Decisions taken
while writing `server/.../HttpServer.kt` and `cli/.../ServeCommand.kt`:

1. **The server is a third daemon over one stored workspace.**
   `jdx serve` (default workspace `default`) resolves roots per request
   through `JdxService.daemonRoots` — the same seam the socket daemon
   (T-082) and MCP (T-043) use — so `ws create` while the server runs is
   picked up, and a missing workspace reads as exit 4 naming the fix. A
   `?workspace=` query argument overrides the server default for that call
   (the MCP per-call override, D-060 §2); a batch takes it on the POST URL
   for the whole batch, because `RpcRequest` lines carry no workspace field.
2. **Bodies are the `--json` envelope verbatim; only the status is new.**
   Every route returns `ServiceOutcome.toJson(wire)` bytes exactly (the
   T-046 parity shape — the tier-2 suite pins GET and batch lines against
   the in-process call), with the exit code mapped to HTTP status in one
   place (`statusForExit`: 0→200, 1→404, 2→300, 3→400, 4→404, 5→502,
   6→500). The CLI's trailing `println` newline is the transport's
   framing, not the envelope — same modulo as the MCP proof.
3. **GET is a query, POST is a batch, and nothing else is a guess.**
   `GET /v1/<wire>?query=…&<param>=…` forwards every key except `query`
   and `workspace` verbatim as D-058 wire params; `POST /v1/batch` takes
   NDJSON `RpcRequest` lines (the T-040 framing, shared with `jdx batch`
   stdin) and answers one envelope line per request without aborting on a
   per-query failure (the T-045 rule). Wrong methods, unknown paths and
   malformed query strings read as exit-coded envelopes (405/404/400),
   never a drop. `version`/`health` answer internally in the daemon's
   shapes; `doctor` is refused exit 6 naming `jdx doctor` (`DoctorService`
   lives in `:cli`).
4. **Localhost by default, separate socket from the daemon.**
   `DEFAULT_HTTP_BIND` (`127.0.0.1`) and `DEFAULT_HTTP_PORT` (`7070`) are
   pinned constants; binding anything else is explicit. No idle shutdown —
   `serve` blocks until interrupted, like `daemon run` without the timer.
5. **`ServeCommand` stays thin via an injectable runner.** The blocking
   bind-and-join lives in a `(bind, port, workspace) -> Unit` default, so
   tier-1 pins defaults, flag plumbing and exit 3/6 paths without touching
   a socket (the `DaemonCommand` test seam precedent).

**Status:** proposed-by-implementer. Decided 2026-09-23, session 71 (T-044).

## D-062 — Kotlin sidecar fetch: explicit `jdx kotlin install`, no auto-fetch (T-080) · proposed-by-implementer

**Context:** T-038/T-039 built the D-008 side-load (versioned sidecar path,
isolated loader, PSI queries) but nothing downloads the set: a missing sidecar
degrades every `.kt` query. T-080 left the flag surface open (`--fetch` parity
on the read commands vs a `kotlin install` command vs daemon warm-up).

**Decisions:**
1. **Explicit `jdx kotlin install`, nothing implicit.** No auto-fetch on
   `body`/`source`/`doc` (D-055 §3 already rules it out — the T-019
   no-surprise-network ethos), no daemon warm-up hook. A missing sidecar
   keeps degrading exactly as before; the degrade hints (`kotlinMissingHint`,
   the parser's unavailable detail, the `doctor kotlin` WARN) now name
   `jdx kotlin install` as the fix.
2. **The set is the compiler's dependency closure, pinned.** Seven jars —
   `kotlin-compiler-embeddable`, `kotlin-stdlib`, `kotlin-script-runtime`,
   `kotlin-daemon-embeddable` at `KOTLIN_COMPILER_VERSION`, plus
   `kotlin-reflect 1.6.10`, `kotlinx-coroutines-core-jvm 1.8.0`,
   `annotations 13.0` from the compiler POM — downloaded from Maven
   repositories (Central last, `--repo` mirrors first, T-069 order) with
   SHA-1 verification per jar (`MavenFetch.fetchVerified`, fails closed) and
   atomic writes, so a killed run never probes as installed. Present jars are
   skipped without network; a re-run resumes; `--force` repairs the
   presence-OK/use-degrades split (D-054 §2).
3. **Lives in `index/.../kotlin`, not `sources`.** Fetching needs HTTP +
   SHA-1 + atomic-write, which already exist as `MavenFetch`/`MavenCoords` in
   `:index` — and `:index` already depends on `:sources` for the sidecar
   paths, while `:sources` cannot depend back. The CLI stays thin (D-004):
   `kotlin install [--repo …] [--force] [--json]`, exit 0 ok · 3 bad
   `--repo` · 5 download/checksum/IO failure (the `--coord` mapping, D-015).
   Maintenance commands (`cache`, `daemon`) are not MCP tools, so neither is
   this — no wire/adapter/parity touch.
4. **Reports name files, never paths.** Text and `--json` carry the installed
   vs already-present file names in table order plus the `~/.cache/jdx/kotlin`
   literal — deterministic across machines (CLAUDE.md §2.5).

**Status:** proposed-by-implementer. Decided 2026-09-23, session 80 (T-080).

## D-063 — `@Metadata`-aware `SOURCES_VERSION_MISMATCH` pairing for Kotlin (T-081) · proposed-by-implementer

**Context:** `mismatchWarning` paired over JVM names via `listJavaMembers`,
so every Kotlin pair skipped (`null`): compiler-generated members (data
`componentN`/`copy`, value-class `-impl`s, `@JvmOverloads` overloads,
file-facade statics) would have false-positived a naive pairing.

**Decisions:**
1. **Pair over Kotlin declaration names, not JVM names.** New
   `sources/.../SourcesMismatch.kt:detectKotlinSourcesMismatch` projects
   bytecode into declaration space first: JVM names map through
   `ClassInfo.kotlinMethodViews` (`@JvmName`, mangled `internal`),
   `suspend` drops the trailing `Continuation`, folded
   accessors/backing fields drop out in favour of one `FIELD` row per
   body-declared property (primary-constructor properties pair through the
   `<init>` params instead), extension receivers pair positionally
   (`listedKotlinMembers` counts the receiver — a fix, not a behaviour
   change: its only other consumer checks names).
2. **Excuse, don't match, compiler output — on leftovers only**, so declared
   members always win: `$default` stubs, `componentN`/data-`copy`,
   `-impl`/`equals-impl0`, `DefaultConstructorMarker` ctors (also excluded
   from the implicit-default count, shared with the Java detector),
   generated `toString`/`hashCode`/`equals` only when data/value generation
   is evidenced, `$`-named/holder fields, `@JvmOverloads` shorter overloads,
   and outer statics when a companion holder field evidences a companion
   (companion staleness still warns under the `$Companion` binary).
   Plain-named synthetics are kept (Kotlin `inline`/`reified` impls are
   synthetic yet source-declared); `$`-named ones still filter.
3. **One deliberate leniency: unresolvable source spellings.** A
   `typealias` (`UserId` erasing to `String`) is user-defined per file and
   invisible to bytecode — it pairs by arity against a known JVM type
   rather than warning as noise. Stale changes between two known types, and
   between two unknown names, still warn.
4. **Wiring follows the T-039 parser pattern.** `mismatchWarning` tries Java
   first, then Kotlin when `isKotlin` (shared per-command `ktParser` on
   body/doc/around; a throwaway from `kotlinUserHome` on the whole-file
   `source` path); unavailable/absent stays silent, and the branch never
   throws. Non-Kotlin input to the Kotlin detector delegates to JVM
   pairing.

**Known limitations (documented in the detector KDoc, not silent bugs):**
companion `const` vals live only in the outer bytecode, so a direct
`$Companion` query may warn on them; removing a body-declared property from
sources is not detected.

**Status:** proposed-by-implementer. Decided 2026-09-23, session 81 (T-081).

## D-064 — test-source/Java warnings-as-errors gating scope (T-083) · proposed-by-implementer

**Context:** T-052 gated main Kotlin compilations with `allWarningsAsErrors`
and left test sources + Java to T-083. The test sweep found 11 Kotlin warnings
(opt-in, 5× dropped-message `shouldNotBeNull`, 4× `!!`, 1× deprecated arb) plus
the deliberate `strictfp` fixture warning in Java.

**Decisions:**
1. **`allWarningsAsErrors` on `compileTestKotlin` and
   `compileTestFixturesKotlin`, `-opt-in=io.kotest.common.ExperimentalKotest`
   on `compileTestKotlin` only.** The blanket flag breaks kotest-free
   `compileTestFixturesKotlin` (unresolved opt-in marker is a hard error,
   proven red in-session) — the flag lives only where kotest is on the
   classpath via the shared test dependencies, which is every
   `compileTestKotlin` in the repo.
2. **Java `-Werror` on every `JavaCompile`, no module exclusion.** All Java
   sources in the repo are `testfixtures` fixtures, so excluding
   `testfixtures` (the alternative the T-083 brief offers) would gate zero
   files. The one deliberate warning is suppressed at its declaration
   (`@SuppressWarnings("strictfp")` on `VarargsAndModifiers.fp`, with a
   comment pointing at the gate) — proven to silence it via a `javac`
   scratch test before wiring the gate.
3. **`requireNotNull` over `shouldNotBeNull { msg }` in tests.** The kotest
   overload takes `(T) -> Unit`, so the trailing message string is coerced to
   `Unit` and silently dropped (proven via `javap` on `MatchersKt`) — the
   "unused expression" warning was reporting a real message loss, not noise.
   `requireNotNull` keeps the lazy message and smart-casts.

**Status:** proposed-by-implementer. Decided 2026-09-24, session 82 (T-083).

## D-065 — `doctor` daemon aliveness semantics (T-084) · proposed-by-implementer

**Context:** the `doctor daemon` row counted `.sock` files (an honest placeholder
until the daemon existed). The T-041 daemon answers `health`, so `doctor` can
now report running vs stale per socket.

**Decisions:**
1. **Probe every `*.sock` with `DaemonProbe.health`, injected.** `DoctorService`
   takes `(Path) -> DaemonStatusSnapshot?` defaulting to the real probe — as a
   lambda, not a `::health` reference (a callable reference keeps the defaulted
   `timeoutMs` arity, L-113). A throwing probe reads as stale: the T-005
   never-throws contract covers the probe too.
2. **Stale is WARN, never FAIL.** A stale socket blocks no query, so it must not
   trip the exit-6 law — WARN keeps exit 0 while still naming the housekeeping.
   All-answer → OK, any-stale → WARN.
3. **Name what identifies the socket.** Running rows name sorted workspace names
   (from the health snapshot); stale rows name sorted file names (the hash
   carries no workspace back). Details stay single-line via the existing
   `check()` fold; no-`XDG_RUNTIME_DIR` / missing-dir / no-socket rows are
   unchanged (`not running`, OK).

**Status:** proposed-by-implementer. Decided 2026-09-24, session 83 (T-084).

## D-066 — orphan daemon `.log` gc semantics (T-085) · proposed-by-implementer

**Context:** every spawned daemon leaves a `.log` sibling next to its socket,
and neither idle shutdown nor `daemon stop` removes it (kept as evidence).
With no rotation or `gc` coverage, dead daemons accumulate logs in
`$XDG_RUNTIME_DIR/jdx/` forever.

**Decisions:**
1. **`cache gc` owns orphan daemon logs.** A log is orphaned when its sibling
   `.sock` is absent or no daemon answers there; logs of live daemons are kept
   as running evidence. Dead sockets themselves stay `stop`/`doctor` business.
2. **The sweep runs even when the index DB is absent** (orphan logs do not
   depend on it), but a corrupt-workspace / DB failure (exit 4/6) still fails
   without touching anything — the T-018 "failure deletes nothing" precedent.
3. **Conservative deletion.** Only top-level `*.log` regular files with the
   lowercase suffix the daemon writes; a throwing probe reads as "cannot prove
   orphaned" (keep); IO failures keep; a missing dir sweeps nothing. Never
   throws.
4. **Names, not paths.** The report carries sorted file names (D-007); text
   renders a `daemon logs:` line only when something was (or would be)
   deleted, so seam-off output is byte-identical to before; JSON gains
   `daemonLogsDeleted` + `daemonLogBytesFreed`.
5. **Injectable like every other `CacheService` seam** (`daemonRuntimeDir`,
   default `null` = today's behaviour; `daemonSocketAlive`, default `false`).
   Production wires the real runtime dir plus `DaemonProbe.health` in the CLI
   adapter, which already depends on `:server`.

**Status:** proposed-by-implementer. Decided 2026-09-24, session 84 (T-085).

## D-067 — warm text output via a server-rendered `text` envelope field (T-086) · proposed-by-implementer

**Context:** T-042 serves `--json` warm and leaves text in-process (D-059 §1:
no text wire, so serving warm text would mean rebuilding 17 renderers from
JSON). The deferred follow-up offers two lifts: a text wire or a
JSON→Outcome parser. A JSON→Outcome parser would rebuild all 17 result models
from envelope JSON in the client — a second copy of every renderer input, kept
in sync by discipline. A text wire renders once, where the objects already
exist.

**Decisions:**
1. **Text wire, not a JSON→Outcome parser.** The daemon renders plain text
   server-side into an extra `"text"` envelope field. No client-side model
   reconstruction, no second source of truth for any result shape.
2. **Presentation-only wire params (`warmText`/`warmBrief`/`warmMaxLines`).**
   Unknown params are already ignored on the `--json` path, so old daemons
   ignore them and new ones use them; requests without `warmText` are
   byte-identical to before (T-046 parity untouched). `warmBrief` selects
   `renderBriefText`, `warmMaxLines` caps via `TokenBudget.capLines`; hostile
   values degrade to the plain rendering, never a throw.
3. **Inject, don't re-render the envelope.** `dispatchJson` serialises the
   outcome exactly as before, then inserts `"text"` before the trailing
   `"warnings"` marker (last occurrence, so a result payload containing the
   marker cannot misplace it). A missing marker returns the envelope
   unmodified rather than failing the query.
4. **Warm text is plain (no ANSI).** The daemon has no TTY, so it renders with
   `color=false`; piped output is byte-identical to cold, TTY color is the
   only documented difference. Missing/unparseable `text` (a pre-T-086
   daemon) degrades to in-process, never an error — same rule as every other
   warm refusal.
5. **Only `members`/`outline` forward presentation flags.** Every other
   command's text-affecting flags are already query params on the wire;
   `--brief`/`--max-lines` are the sole text-only pair (T-047), so they are
   the only new client plumbing. Usage errors still fail fast locally before
   any socket IO.

**Status:** proposed-by-implementer. Decided 2026-09-24, session 85 (T-086).
