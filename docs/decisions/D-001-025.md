## D-001 — Implementation language: Kotlin on Gradle
**Status:** locked · **Date:** 2026-09-13 · **Decided by:** owner

Alternatives offered: Java+Gradle, Kotlin+Gradle, Go/Rust native binary, Python.
Owner chose **Kotlin + Gradle**.

**Why it matters:** the JVM ecosystem is the only one with mature bytecode (ASM), source
parsing (JavaParser, Kotlin PSI) and decompilation (Vineflower) libraries. Kotlin gives
terser modelling code, sealed hierarchies, and null-safety for a domain that is full of
"maybe absent" data (no sources jar, no param names, no javadoc).

**Accepted cost:** JVM start-up (~250 ms cold). Mitigated by AppCDS and the daemon (D-004).

## D-002 — Decompiler: bundle Vineflower, keep `javap` as an alternate engine
**Status:** locked · **Date:** 2026-09-13 · **Decided by:** owner

The original brief said "decompiled bytecode using javap". Offered: javap-only,
Vineflower-bundled, or multi-engine. Owner chose **Vineflower bundled as default, javap
available via `--engine javap`**.

**Why:** `javap -c` emits JVM opcodes, which a model must mentally decompile before it can
reason. Vineflower emits readable Java. `javap` is retained because it is *exact* — the
right tool when the question is genuinely about bytecode.

**Note:** Vineflower is Apache-2.0 and already present in this machine's Gradle cache
(Fabric Loom uses it). Multi-engine (CFR/Procyon) is phase 2, not rejected.

## D-004 — Interfaces: CLI + MCP + daemon + HTTP, all four
**Status:** locked · **Date:** 2026-09-13 · **Decided by:** owner

Owner selected all four, with two explicit notes quoted verbatim:

> "for the background daemon - it can have a timer for shutdown - after 5 minutes of
> inactivity it go down. this is very simple :)"

> "also the http/json serves completely a different purpose on different port/socket/stream.

**Therefore:** daemon idle timeout defaults to **5 minutes**, configurable via `--idle`,

**Architectural obligation:** because there are four front-ends, *no behaviour may live in a
front-end*. All four are adapters over one `JdxService`. See CLAUDE.md §4.

## D-008 — Kotlin: `@Metadata` + full `kotlin-compiler-embeddable` PSI parsing
**Status:** locked · **Date:** 2026-09-13 · **Decided by:** owner

Offered: metadata + lightweight lexer-based `.kt` extractor; metadata + full PSI; or JVM-view
only. Owner chose **full PSI**, accepting the stated ~55 MB / ~1 s cost.

**Mandatory mitigations** (`proposed-by-implementer`, see PROPOSAL.md §12.2):
1. Behind a `SourceParser` interface — nothing outside `sources/` may import Kotlin compiler
   classes.
2. Lazily loaded, in an **isolated `URLClassLoader`** (it shades Guava and IntelliJ platform
   classes that will otherwise collide).
3. Side-loaded jar fetched/verified on first use — **not** in the main fat jar.
4. Initialised once per daemon lifetime.
5. `jdx doctor` reports whether it is installed.

If these mitigations prove impossible, **stop and ask the owner** rather than silently
shipping a 60 MB CLI with a 1-second floor on every invocation.

## D-009 — Truth model: bytecode is the skeleton, sources are the flesh
**Status:** locked · **Date:** 2026-09-13 · **Decided by:** owner

Structure (which members exist, modifiers, descriptors, generic signatures, supertypes,
annotations) always comes from **bytecode**. Sources supply **bodies, real parameter names,
javadoc/KDoc, and comments**. A sources jar that disagrees with its binary produces a
`SOURCES_VERSION_MISMATCH` warning — it never silently wins.

**Why:** a mismatched or stale sources jar is a common packaging bug. Taking structure from
the binary means `jdx` cannot be lied to about the API surface.

## D-013 — Index storage engine: SQLite (single global DB, artifact-scoped rows)
**Status:** proposed-by-implementer · **Date:** 2026-09-13

One database at `~/.cache/jdx/index/v1.db` in WAL mode. Every row scoped by `artifact_id`
= content hash of the binary jar. A workspace is an ordered list of `artifact_id`s.

**Why not a custom binary format:** we would have to write and maintain an on-disk hash
index to answer `usages` queries; SQLite already has B-trees, transactions, WAL concurrency
and a query planner.
**Why not one DB per workspace:** artifacts would be re-indexed per workspace, and 2,000-jar
workspaces exceed SQLite's `ATTACH` limit.
**Why not an in-process embedded KV (MapDB/LMDB):** `usages` needs secondary indexes on
several columns; that is a relational query.

**Reversible.** The store is behind an `IndexStore` interface. If SQLite's ~12 MB of bundled
native libraries becomes unacceptable, swap the implementation.

## D-014 — Symbol reference syntax: javadoc-style `Type#member(params)`
**Status:** proposed-by-implementer · **Date:** 2026-09-13

Canonical form is `com.google.gson.Gson#toJson(java.lang.Object)`. Input is parsed
generously (`.`/`::`/`#` separators, simple or FQ params, bare descriptors, short type
names). Full grammar in PROPOSAL.md §6.

**Why:** it is the form Java developers, javadoc, stack traces, and LLM training data
already use. Familiarity beats novelty for a syntax an agent must produce from memory.

## D-016 — Ambiguity is a result, not an error
**Status:** proposed-by-implementer · **Date:** 2026-09-13

`jdx` never guesses which overload or which shaded copy of a class the user meant. It exits
`2` and prints every candidate as a copy-pasteable canonical ref.

**Why:** a CLI has no chooser dialog, and a wrong guess produces confidently-wrong agent
output — the worst failure mode this tool can have.

---

## D-017 — Read-only, never executes inspected code
**Status:** proposed-by-implementer · **Date:** 2026-09-13

`jdx` writes only to `~/.cache/jdx` and `~/.config/jdx`. It parses class files with ASM and
never loads them into the JVM, so no static initialiser from an inspected artifact ever runs.

**Why:** agents inspect untrusted third-party jars. This property must not be traded away for
convenience (e.g. do not "just use reflection" to read a class — it is not equivalent).

## D-019 — Documentation-for-successors is a release gate
**Status:** locked · **Date:** 2026-09-13 · **Decided by:** owner

Raised by the owner mid-session (quoted in D-012). The project is developed by a rotating
cast of agents and humans with different styles and no shared memory.

**Therefore, these are gates, not suggestions:**
1. `docs/PROGRESS.md` is appended to at the end of **every** working session, using its
   template. A session that changed files and left no log entry is an incomplete session.
2. `docs/TASKS.md` is the single source of truth for "what to do next". Task status is
   updated *as work happens*, not retroactively.
3. Every non-obvious decision made while coding gets an entry here.

5. Any command that ships without `--help` text, a JSON renderer, a test, and a README row
   is not finished.

## D-020 — Testing strategy: TDD for `core`, plus five self-generating test families
**Status:** locked · **Date:** 2026-09-13 · **Decided by:** owner (delegated the method)

Owner's instruction, verbatim:

> "because this a heavy project it also needs heavy testing. I'm thinking of TDD, but if you
> know a better way go with that. (don't stand with small and a few test cases; more tests
> guarantee less bug)"

**Decision:** TDD is adopted and is **mandatory for `core`** — but TDD alone is explicitly
judged insufficient for this project, and is paired with nine other test families. Full
strategy in `docs/TESTING.md`; summary in `docs/PROPOSAL.md` §18.

**Reasoning (the part worth preserving):** TDD verifies behaviour *you* defined. Roughly 40 %
of `jdx` is like that — the ref grammar, member resolution, generic substitution, truncation,
rendering — and TDD fits it perfectly. The other 60 % reads files produced by other people's
compilers, where the correct answer is "whatever `javac` actually emitted" and cannot be
invented in a test. For that half, hand-written examples plateau quickly. So the strategy
favours families that **generate their own cases**:

- **Differential testing against `javap`** — a free, exhaustive oracle for bytecode reading.
  One harness covers access flags, bridges, synthetics, varargs, enums, records and nested
  classes without anyone enumerating them.
- **Compile-back testing** for decompilation — assert the decompiled source recompiles to the
  same API surface, rather than pinning decompiler text that changes every release.
- **Property-based testing** for parsers and resolvers (≥ 1,000 cases each; failing seeds get
  pinned as regressions).
- **Metamorphic testing** for relations that must hold between answers
  (`hierarchy --up` ⟺ `--down`, `callers` ⟺ `calls`, `--inherited` ⊇ `--declared`,
  run-twice determinism).
- **Fault injection** for the "degrade, don't fail" promise (zip-slip, zip bombs, truncated
  classes, mismatched sources jars, `-g:none`, decompiler timeouts).
- **Corpus soak** over the ~2,183 real jars on the owner's machine — asserting *invariants*
  (never crash, always valid JSON, always deterministic) rather than values.
- **Mutation testing (Pitest)** as the meta-test: line coverage measures which code ran;
  mutation score measures whether the tests would notice if it were wrong. This is the direct
  answer to "don't stand with a few test cases". `core` is gated at **≥ 80 %**.

**Enforced budgets** (`proposed-by-implementer`, change freely if they prove wrong):
`./gradlew test` **< 30 s**, `./gradlew check` **< 3 min**. A slow inner loop kills TDD, and
then it kills testing. Corpus, benchmark and mutation runs are tagged off by default.

## D-021 — Test tiers, coverage gates and the golden-file hazard
**Status:** proposed-by-implementer · **Date:** 2026-09-13

Four tiers: `test` (tier 1, TDD loop) · `check` (tier 2, pre-commit) · `soak` (tier 3,
needs local jars, tagged) · `bench` + `mutationTest` (tier 4, on demand).

Gates: `core` ≥ 95 % line and ≥ 80 % mutation score. `index`/`sources`/`decompile` ≥ 85 %
line, mutation measured and reported but not gated. `cli`/`mcp`/`server` have **no coverage
gate** — they are thin by rule (D-004) and are covered by parity and golden tests instead.
Gating thin adapters would only incentivise padding.

**Golden files:** `-Pgolden.update=true` is the most dangerous command in the repo — it makes
every failing output test pass instantly, correct or not. The rule is: **always read the
diff before committing it.** A golden file updated without reading is a test that has been
deleted.

## D-022 — Work cadence: one small task → commit → push → log → next task
**Status:** locked · **Date:** 2026-09-13 · **Decided by:** owner

Owner's instruction, verbatim:

> "also prefer: small task -> commit/push -> log -> next task -> ..."

**The loop every contributor follows:**

1. Pick the lowest-numbered unblocked `TODO` in `docs/TASKS.md`.
2. Set it `WIP` and **commit that change first**, so parallel contributors don't collide.
3. Do **only** that task. Do not fold adjacent work in — file a new task instead.
4. Make it green: tiers 1 and 2 of `docs/TESTING.md`, plus tier 3 if you touched artifact
   reading, indexing or rendering.
5. Commit with a Conventional Commit naming the task: `feat(index): parallel indexer (T-014)`.
6. **Push.**
7. Set the task `DONE` in `docs/TASKS.md`, append a session entry to `docs/PROGRESS.md`, and
   update its `CURRENT STATE` block. Commit and push that too.
8. Next task.

**Why this cadence and not "finish the milestone, then commit":** the project is worked on by
contributors who share no memory (D-019). An unpushed, unlogged working tree is invisible to
everyone else — if the session ends there, the work is effectively lost and the next
contributor may redo it. Small pushed increments also mean `git bisect` works, reviews are
possible, and a bad task can be reverted without unpicking four others.

**Consequence for task sizing:** if a task cannot be finished, committed and logged in one
sitting, it is too big — **split it in `docs/TASKS.md` first**, then do the first half. This is
a normal and expected thing to do, not an admission of failure.

**Push caveat that still stands:** an agent needs an explicit owner go-ahead in the current
conversation before the *first* push of a session to a public remote (D-012). Once given,
this cadence is the default for that session.

## D-023 — Ever-growing documents are sharded; entry files stay small
**Status:** locked · **Date:** 2026-09-13 · **Decided by:** owner

Owner instruction: *"if a document of this project is ever growing like the PROGRESS.md it
must be sharded (just as an example progress1-10, progress11-20, etc…)"* — with the driver
stated explicitly: **agent context efficiency. Use references; read only when needed.**

**The pattern:** every append-only log has a small *entry file* (rules, index, template,
live handoff block) and *shard files* that hold the entries. An agent reads the entry
file, then opens exactly the shard it needs. Moving an entry into a shard is a
restructure noted in the session log — past entries are never rewritten.

| Log | Entry file | Shards | Capacity |
|---|---|---|---|
| Session log | `docs/PROGRESS.md` (CURRENT STATE + index + template) | `docs/progress/sessions-001-010.md`, … | 10 sessions |
| Decisions | `docs/DECISIONS.md` (rules + index) | `docs/decisions/D-001-025.md`, … | 25 decisions |
| Lessons | `docs/LESSONS.md` (rules + index) | `docs/lessons/L-001-025.md`, … | 25 lessons |

**Scope:** the rule covers *append-only* logs. Curated documents (`docs/TASKS.md`,
`CLAUDE.md`) are edited in place, not sharded; if `TASKS.md` ever grows unwieldy, split it
per milestone — a different operation with the same goal. Shard capacities are
`proposed-by-implementer` defaults and may be retuned; the sharding itself is locked.

## D-024 — Every hard-won lesson is recorded in `docs/LESSONS.md`
**Status:** locked · **Date:** 2026-09-13 · **Decided by:** owner

Owner instruction: *"any experience you and anyone else get, should be documented
somewhere, to prevent later agents do the same mistake."*

**Therefore:** `docs/LESSONS.md` is the durable, numbered (`L-nnn`) log of mistakes made
and their fixes, toolchain quirks, and spec gotchas. Full rules live in that file; the
shape:

- Anything that cost more than a few minutes **and could cost another contributor the
  same** becomes an entry, tagged (`build`, `tooling`, `jvm-spec`, `kotlin`, `process`).
- Entries are short — symptom, cause, fix, and a pointer to the session/task that learned
  it. Narrative stays in the session log; the lesson is the distilled fact.
- No duplication: environment facts live in `CLAUDE.md` §8, rationale in
  `docs/DECISIONS.md` — lessons reference those instead of restating them.
- Sharded per D-023 (25 per shard). Seeded in session 4 with nine lessons (L-001…L-009)
  distilled from sessions 1–3.

A session that learned something and logged no lesson is incomplete — the same spirit as
D-019.
