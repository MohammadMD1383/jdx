### D-026 — Launcher environment resolution and its exit code (T-004) · proposed-by-implementer

**Context:** the `jdx` launcher (`app/src/main/scripts/jdx`) runs *before* any JVM exists,
so D-015's exit-code contract — written for query results — does not literally apply to its
failures. The task still demands "a human error, not a stack trace".

**Decisions:**
1. Launcher-level failures print one `jdx: <reason>` line on stderr and **exit 6**. Reusing
   D-015's "internal error" keeps the observable contract total: any nonzero exit maps to
   a documented code, so agents can branch without new cases.
2. **A set-but-broken `JAVA_HOME` is a hard error**, not a silent fall-through to `java` on
   PATH. An explicit `JAVA_HOME` is a strong user signal; quietly picking another JDK hides
   the real problem and can inspect bytecode with a different JDK than intended.
3. Resolution order is `JAVA_HOME` → `java` on PATH → `$JDX_JVM_DEFAULT_DIR` (default
   `/usr/lib/jvm/default`, the Arch layout). The override exists mainly so the no-JDK error
   path is testable on machines that always have a JDK, and secondarily for non-Arch users.
4. The minimum JDK is a **hard gate at major 21** (the bytecode target), checked *before*
   exec: an old JDK cannot even load Java-21 class files, and its `UnsupportedClassVersionError`
   stack trace is exactly what this gate exists to prevent.
5. The launcher depends on exactly one external tool, `sed` (checked up front); `dirname` is
   avoided in favour of POSIX parameter expansion and `readlink` is optional, so a broken
   PATH still yields one clean error.

**Status:** proposed-by-implementer. Decided 2026-09-14, session 6 (T-004).

### D-027 — `doctor` severity policy, M0 envelope shape, `--json` positions (T-005) · proposed-by-implementer

**Context:** `jdx doctor` must assign OK/WARN/FAIL to checks, some for milestones that do
not exist yet, and `jdx version`/`doctor --json` need an envelope before T-010 builds the
shared renderers.

**Decisions:**
1. Severity rule: **FAIL** = jdx cannot do its core job here (unreachable `jrt-fs`,
   missing/unrunnable `javap`, unwritable cache, a check that throws); **WARN** = degraded
   or not-yet-available (absent `src.zip` per T-012, `javap` older than 21, missing cache/
   config/index/Kotlin module); **OK** = fine, including correctly-absent (no daemon, no
   workspace). WARN never affects the exit code.
2. Missing `javap` is FAIL, not WARN: a machine without it cannot run the `javap`
   differential oracle (T-056) or the `javap` decompile engine (T-027), and an unreachable
   FAIL state would leave the exit-6 contract untestable in M0.
3. M0 envelope is the minimal `{"jdx": 1, "ok", "command", "result"}` — no `query`,
   `truncated`, `warnings` or `provenance` until T-010 answers them. `ok` mirrors the exit
   code (`false` iff any FAIL), so agents can branch on either signal identically.
4. `--json` is accepted **before or after** the subcommand name (`jdx --json doctor`,
   `jdx doctor --json`): the flag lives on the root and on each JSON-capable subcommand,
   effective when either is set. True global-flag plumbing (either position for every
   flag) arrives with the T-011 flag pass; until then per-command flags are the mechanism.
5. Cache/config roots are the literal `~/.cache/jdx` and `~/.config/jdx` (D-013, T-015) —
   no `XDG_*` fallback. Doctor is read-only: it never creates the directories it reports.

**Status:** proposed-by-implementer. Decided 2026-09-14, session 7 (T-005).

### D-028 — Renderer placement, signature layout, and the JSON contract (T-010) · proposed-by-implementer

**Context:** T-010 builds the shared text+JSON renderers that T-011's
`show`/`outline`/`members` commands will consume. `core` must stay
dependency-free (CONTRIBUTING.md), so JSON has nowhere to come from.

**Decisions:**
1. Renderers live in `core/.../render/` (pure data + pure functions, test-first
   like the rest of `core`). JSON is **hand-rolled string code** (`JsonEscape` +
   per-model `toJson`), not kotlinx-serialization — the same reason descriptor
   parsing lives in `core`. The cli tier-2 suite parses our output with
   kotlinx.serialization as the outside check. `cli/.../render/JsonEnvelope.kt`
   (M0 seed, D-027) stays until a later task migrates `version`/`doctor` onto
   the shared envelope; the two shapes are compatible (T-010 only *adds* the
   optional `query`/`truncated`/`warnings`/`provenance` fields, envelope stays
   version 1).
2. Signature lines use **fully-qualified `$`-joined types**
   (`java.util.Map$Entry`, `java.lang.String[]`). This overrules the
   simple-name illustration in PROPOSAL.md Appendix A: with FQNs a text line
   plus its group header is mechanically canonical
   (`HeaderType#name(fqn-params)`), and two same-named types in different
   packages can never print identically (never-guess, D-016). JSON rows carry
   the exact canonical `ref` string regardless.
3. Grouped output reads principle 3 ("every output line names its symbol")
   per-group: headers carry the declaring type once (§8.1), lines carry kind +
   full signature. Constructors print under the simple class name
   (`public Point(int x)`), never `<init>`.
4. `java.lang.Object` members collapse to one `+ N from java.lang.Object
   (--from java.lang.Object to expand)` line by default (PROPOSAL.md §7.1);
   within a group rows sort by signature text, tie-broken by ref. Truncation
   cuts whole rows most-valuable-first (default cap 50, hint `--limit <total>`)
   and the Object summary line is pinned chrome, never counted.
5. `ErrorResult` (exit 1 not-found with did-you-mean refs, exit 2 ambiguous
   with every candidate) renders in text per §6/§16 and in JSON as
   `ok:false` + `error:{code,message}` + `candidates[]` (candidates double for
   suggestions — one uniform shape).
6. New warning code `UNRESOLVED_SUPERTYPE` for hierarchy edges the workspace
   cannot provide (PROPOSAL.md §16 list updated in the same commit, per the
   `Warning` KDoc rule). Missing supertypes are skipped rows + a labelled
   warning, never silent holes.
7. Golden hermeticity rule: goldens use a fixed artifact label (never the real
   jar filename), an empty `java.lang.Object` stub plus fixture classes only
   (no JRT — JDK-version-dependent goldens are forbidden), and fail on
   orphaned files. The Object-collapse path with real members is covered in
   core's example tests instead.

**Status:** proposed-by-implementer. Decided 2026-09-16, session 13 (T-010).

### D-029 — Workspace file shape and resolution semantics (T-015) · proposed-by-implementer

**Context:** T-015 turns PROPOSAL.md §5.3/§13 into files and flags: TOML workspaces,
ordered roots, `ws use`, `JDX_WORKSPACE`, `-w` on read commands.

**Decisions:**
1. File shape is exactly three keys (`name`, `jars`, `include_jdk`; `includeJdk`
   accepted as an alias) via a hand-rolled codec (`index/.../workspace/WorkspaceToml`),
   not a TOML library — the schema is three scalars and determinism matters. Unknown
   keys are rejected (a typoed key silently doing nothing misleads worse than an
   error); a `name` disagreeing with the file stem is corrupt. If the schema grows
   past this, adopt a real library instead of extending the parser.
2. Names match `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$` — file stems, so traversal-proof
   by construction. The default lives in `~/.config/jdx/active-workspace` (one name;
   garbage reads as none, never a failure).
3. Roots merge explicit-first: `--jars` in front of the workspace's jars, so flags
   shadow the workspace exactly as earlier classpath entries shadow later ones.
   `--no-jdk` always wins; there is deliberately no `--jdk` flag on read commands —
   the workspace owns the JDK default.
4. `ws create` refuses an existing name (exit 1) rather than overwriting crafted
   order; `ws add` extends, `ws remove` replaces. `--src`/`--coord` on `create`
   fail naming T-016/T-019 instead of storing roots no reader honours.
5. Exit mapping: unknown workspace → 1 for `ws` management, 4 for read queries
   (the workspace cannot be resolved); corrupt file → 4 everywhere; other IO → 6.
   `ws list` still lists a corrupt file's name — one bad file never hides the rest.
6. Shadowing/`DUPLICATE_FQN` needed no new code: `JdxService` already resolves
   first-provider-wins over ordered roots — the workspace only supplies the order.

**Status:** proposed-by-implementer. Decided 2026-09-16, session 20 (T-015).

### D-030 — Project auto-discovery semantics and its deliberate deviations (T-016) · proposed-by-implementer

**Context:** PROPOSAL.md §13 step 4 says: walk up for build markers, assemble
`src/main` + `build/classes` + referenced dependency jars, fall back to "a broader
cache scan with a warning" when the reference set can't be determined, cache the
derived workspace under `~/.cache/jdx/auto/<project-hash>.toml`.

**Decisions:**
1. **No broad cache scan, ever.** Scanning every cached jar for an undeterminable
   project would add thousands of unrelated roots — non-deterministic across
   machines, slow, and a shadowing lottery. The fallback is "project classes only"
   plus a labelled `PROJECT_DISCOVERY_FALLBACK` warning (new closed-set code,
   PROPOSAL.md §16 updated) naming the project root and suggesting `--jars`.
2. **Never runs Gradle or Maven (N3).** Coordinates come from `gradle.lockfile` and
   quoted `group:name:version` literals in `*.gradle(.kts)` (regex), plus `pom.xml`
   `<dependency>` entries (hardened `DocumentBuilder`, no doctypes/entities).
   `pom` versions containing `${…}` placeholders are skipped — resolving them would
   mean evaluating the build.
3. **Deepest class dirs, not outermost.** `DirArtifact` entries are relative to the
   opened root, so only true package roots are usable: `build/classes/java/main`
   (and `kotlin/main`) beat `build/classes`; a lone `build/classes` stays a root
   only with no language layout beneath it. `target/classes` for Maven.
4. **Discovery fills the workspace half only when no named workspace is selected**
   (`-w`/`JDX_WORKSPACE`/`ws use` all beat it); explicit `--jars` merge in front
   of discovered roots; `--no-jdk` still wins. No new flags, no opt-out env var.
5. **Cache is `<hash>.toml` + `<hash>.fingerprint`,** where hash = SHA-256/128 of
   the normalised root path (a valid workspace stem, so the `WorkspaceToml`
   stem rule holds with `name == hash`) and the fingerprint covers every existing
   marker/lock/pom file's bytes. Any build-file change invalidates; corrupt,
   missing or mismatched entries read as absent (re-derive), never as errors.
   The fallback warning is re-derived from the cheap coordinate parse on cache
   hits, so cached and fresh derivations warn identically.
6. **v1 derives binary roots only** — `src/main/{java,kotlin}` are recognised as
   project evidence only via their markers, never added as roots. Stored
   workspaces still reject `--src` (now naming T-031, not T-016).

**Status:** proposed-by-implementer. Decided 2026-09-16, session 22 (T-016).

### D-031 — Search, resolve, ls and tree semantics (T-017) · proposed-by-implementer

**Context:** PROPOSAL.md §7.2 names the four commands and their flags but leaves
the matching semantics open: when is a pattern a glob, what does a bare word
match, what does the default `--kind` cover, and what do `ls`/`tree` list.

**Decisions:**
1. **Mode order: `--regex`, then glob, then plain word.** A pattern carrying
   `*?[{` is a glob (`{a,b}` is accepted as a marker but matches literally —
   brace expansion is a non-goal); anything else is a plain word. `--regex`
   forces regex mode, where an invalid pattern is exit 3, never a throw.
2. **A dotted plain word names a location; a bare word searches.** `dev.jdx`
   `.fixtures.Generics` matches exactly or as a `.`-boundary suffix (so it
   finds that type but not `Generics$Recursive` — the TESTING.md metamorphic
   law `search(exact-fqn-of(T)) == T`). A bare word is a case-insensitive
   substring or a camel-hump on the simple name (`JsonAdapter` finds
   `JsonAdapterAnnotationTypeAdapterFactory`, per the Appendix A example).
   Dotted globs try binary and dotted forms; bare globs try the simple name
   and the binary.
3. **Default `--kind` (`all`) is types + packages + modules — not members.**
   Member search (`--kind method|field`) parses every in-scope class (the slow
   path); running it by default would make every `search` pay a full-workspace
   ASM scan. Index-backed member search will lift this with the M4 graph work.
   `--kind type` is all type kinds; Kotlin `object`/`companion` keep their own
   words beyond the proposal's list. Bridge/synthetic members stay hidden in
   member search, mirroring `members`.
4. **`resolve` is exact-match (exit 0 on several — that is its point; exit 1
   with did-you-mean on none).** `#`/`::` splits the member part; an exact
   package name resolves to its providers. `search` misses exit 1 with
   did-you-mean; `--fuzzy` retries within Levenshtein 2 on simple names.
5. **`ls` lists packages-with-counts for a glob, types for an exact package.**
   `tree [artifact-glob]` groups JRT entries by module and jars by display
   label (`(2)`-suffixed on same-name collisions); `--depth` caps nesting,
   `--counts` adds subtree rollups. Search lists one hit per provider for
   shadowing duplicates instead of warning — the explicit list *is* the answer.
6. **Live roots, no persistent index yet.** Like T-011's reads, these commands
   enumerate entry names and ASM-parse only what the pattern touches (except
   member search, which parses the scope). Correctness first; the M2 demo gate
   ("instant") is honoured for the common type/package paths, not yet for
   member scans over JDK-scale workspaces.

**Status:** proposed-by-implementer. Decided 2026-09-17, session 24 (T-017).

### D-032 — Maven coordinate resolution and fetching semantics (T-019) · proposed-by-implementer

**Context:** PROPOSAL.md §13 promises `--coord g:a:v` roots plus a `g:a:v/` ref
prefix, resolved from local caches first and fetched from Maven Central only
with opt-in `--fetch` (D-006). The details below are the implementer's defaults.

**Decisions:**
1. **Lookup order: fetch cache → Gradle → `~/.m2` → Central.** Our own
   `~/.cache/jdx/m2` (an `~/.m2`-shaped layout) wins so a verified download is
   never re-resolved elsewhere; then `modules-2/files-2.1` (exact
   `<name>-<version>.jar` preferred, else first sorted binary jar), then
   `~/.m2/repository` (exact name only). Gradle `files-2.1` and `~/.m2` roots
   are shared with T-016's `resolveDependencyJars` by layout, not by code
   (that walk excludes sources/javadoc for a different purpose).
2. **Checksums fail closed.** The `.sha1` beside the artifact must exist and
   match (first whitespace-separated token, case-insensitive) or nothing is
   written — an unverified artifact never lands in the cache (PROPOSAL §17).
3. **Sources ride best-effort.** The `-sources.jar` is fetched alongside the
   binary when present upstream; its absence degrades the query to bytecode,
   never fails it. Sibling pairing (`SourcesPairing` rule 1) needs no change:
   the cache layout keeps both files side by side.
4. **Scope, not filter, for `g:a:v/` prefixes.** The coordinate's jar reads
   *first* (shadowing order) and candidates match inside it only — but
   supertypes still resolve from the full workspace behind it, so inherited
   members stay correct. Explicit `--coord` jars merge like `--jars`;
   stored workspace coords resolve *behind* the workspace's jars.
5. **Exit mapping:** malformed `g:a:v` is exit 3 (usage, before any IO);
   absent-but-well-formed without `--fetch` is exit 5 naming `--fetch`;
   fetch/network/checksum failures are exit 5; only resolver-internal bugs
   are exit 6. A stored workspace coord that stops resolving fails the query
   (exit 5) rather than silently dropping a root.
6. **No `--repo` flag in v1.** The Central base URL is a code parameter
   (`Repositories.repoBaseUrl`, default `https://repo.maven.apache.org/maven2/`)
   so corporate mirrors stay possible — the CLI flag is filed as T-069.
   *(Superseded by D-034: T-069 implemented `--repo` in session 37.)*

**Status:** proposed-by-implementer. Decided 2026-09-17, session 28 (T-019).

### D-033 — Member `--sort` order semantics (T-062) · proposed-by-implementer

**Context:** PROPOSAL.md §7.1 promises `--sort name|kind|declaring` (default
`kind` then `name`) but never says what `name` and `declaring` lay out. The
listing renders grouped headers (`<kind> declared on|inherited from <type>`,
D-028), so "flat" needs a definition that keeps headers truthful.

**Decisions:**
1. **`kind` (default) is the T-010 layout, byte-identically:** groups in
   linearisation order (target first, `java.lang.Object` last), kind-minor
   within a declaring type, rows by signature text then ref. Proven by the new
   sort goldens' `kind` files matching the existing default goldens byte for
   byte — any future change to the default must explain itself here.
2. **`declaring` is alphabetical by declaring-type binary name, then kind;**
   rows inside each group sort exactly as `kind`. It differs from `kind`
   whenever hierarchy names do not sort alphabetically (e.g. `TrafficLight$1`
   after `TrafficLight` alphabetically, first by linearisation).
3. **`name` is strictly flat:** every eligible row sorted by raw member name
   (`<init>` sorts as `<init>`, case-sensitive natural order), then signature,
   canonical ref, declaring type and depth. Groups are run-length runs along
   that order — a new group each time the declaring type or kind changes — so
   a kind header may repeat when names interleave across kinds. Flattening the
   groups yields the globally sorted sequence in text and JSON alike (D-007),
   and truncation keeps its prefix.
4. **Plumbing:** the order lives in `JdxService.MemberFilters.sort` (default
   `KIND`), not as a new `members()`/`outline()` parameter, so the
   thin-adapter `MemberQuery` arity stays stable across front-ends (D-004).
   Rows carry `memberName` for the comparator; it is absent from JSON (the ref
   already names the member — text⊆JSON unchanged).

**Status:** proposed-by-implementer. Decided 2026-09-19, session 31 (T-062).

### D-034 — Configurable Maven repositories (`--repo`) semantics (T-069) · proposed-by-implementer

**Context:** D-032 §6 deferred the repository flag ("no `--repo` flag in v1;
the Central base URL is a code parameter"). T-069 implements it: `--repo <url>`
(repeatable) on all seven read commands and `ws create`.

**Decisions:**
1. **Custom mirrors first, Central last.** The fetch order is explicit
   `--repo` values in flag order, then the selected workspace's stored repos,
   then Maven Central — unless Central was named explicitly, in which case it
   stays where named. First checksum-verified binary wins; sources ride
   alongside from the same mirror best-effort. Pre-`--repo` behaviour (Central
   alone) is byte-identical.
2. **Validation is exit 3 naming the value.** Only `http(s)` URLs with a host
   and no query/fragment are accepted (a base is a path prefix joined by
   `downloadUrl`, so `?`/`#` would corrupt every fetch URL). The trailing
   slash is optional. Explicit flags fail fast before IO; stored workspace
   values fail the same way after selection. `ws create --repo` validates
   before storing.
3. **Storage mirrors `--coord`.** `WorkspaceDefinition.repos` persists as an
   optional TOML `repos` key (pre-repos files decode to empty); explicit and
   stored repos combine like explicit and stored coords, and both serve
   explicit `--coord` jars and `g:a:v/` prefix queries through the same
   combined `Repositories`.
4. **Model change, not just plumbing:** `Repositories.repoBaseUrl: String`
   became `repoBaseUrls: List<String>` (with a `repoBaseUrl` first-element
   shorthand kept for message formatting). Fetch tries each base in order.

**Status:** proposed-by-implementer. Decided 2026-09-19, session 37 (T-069).
Supersedes D-032 §6.

### D-035 — `jdx body` output semantics (T-022) · proposed-by-implementer

**Context:** T-022 wires the T-021 seam to `jdx body` with no decompiler yet
(T-026/T-027), no Kotlin bodies (T-039), no doc/signature enrichment
(T-025/T-024) and no `srcmap` (T-020).

**Decisions:**
1. **Canonical refs print erased descriptors** (`identity(java.lang.Object)`,
   never `identity(U)`): structure is bytecode-authoritative (D-009) and the
   listing layer already renders that way — body matches it. Type-variable
   spellings still *resolve* (via the generic signature), they just never print.
2. **Overload ambiguity is decided from bytecode before sources are read**,
   so a stale sources jar cannot mislead. Source lookup then retries with the
   generic signature's spellings when the query came in erased form.
3. **Provenance names the sources file** (`…-sources.jar · path/To.java:a-b`,
   PROPOSAL.md §3.5), not the binary — shadowing stays in the `DUPLICATE_FQN`
   warning. Root-level degradations (no sources, `.kt`-only, source-missing
   member) are exit 1 with a `detail` line naming the owning task, not bare.
4. **Type refs are exit 3 naming `source` (T-023)** rather than a whole-file
   body: `body` is member-scoped, and whole-file slicing belongs to `source`.
5. **Presentation defaults:** `--max-lines 200` (fixture/typical methods are
   far smaller, so the default is invisible until it matters), `--context 0`,
   verbatim unindented body lines, `N | `-prefixed lines under
   `--line-numbers`, `next: jdx show <declaringType>`.
6. **`index` depends on `sources`** (new edge; `sources` still never depends on
   `index`, `core` stays dependency-free): the `JdxService` facade owns the
   binary→sources pairing so `cli` stays thin (D-004).

**Status:** proposed-by-implementer. Decided 2026-09-20, session 41 (T-022).

### D-036 — `jdx source` output semantics (T-023) · proposed-by-implementer

**Context:** T-023 wires the T-021 seam to `jdx source` (whole files/slices
from paired Java sources) with no decompiler yet (T-026/T-027), no Kotlin
bodies (T-039), no doc/signature enrichment (T-025/T-024) and no `srcmap`
(T-020). It mirrors T-022's `body` the way `body` mirrored T-011's reads.

**Decisions:**
1. **Type-scoped, with `--around` as the member entry point.** `source`
   takes a type ref; a member ref exits 3 naming both `jdx body` and
   `--around '<ref>'` — the mirror of D-035 §4 (body's type refs name
   `source`). A bare `--around` name with no `#` parses as a type, so it is
   rejected the same way; pass the full member ref.
2. **Whole files and `--lines` windows are verbatim text, never parsed.**
   Only `--around` parses (via `findJavaBodies`) to locate the member. A
   `.kt` path still degrades to exit 1 naming T-039: `findSource` happily
   returns the `.kt` file when that is all there is, and facade/class
   mapping makes raw serving potentially misleading — `body` never sees this
   because `findJavaBodies` filters `NotJava` first (L-069).
3. **`--lines A:B` is 1-based inclusive over the served numbering** (after
   the §4 drop): the end clamps to the file, a start beyond EOF is exit 1
   naming the range and the file length. `--lines` and `--around` are
   mutually exclusive (exit 3); `--context` needs `--around` (exit 3 at the
   CLI — a whole file has no center — and the service also rejects
   `--lines`+`--context` in depth).
4. **One trailing empty line is dropped** when a file ends with a newline:
   otherwise `split('\n')` reports a phantom extra line (a 38-line file
   prints `1-39`, off by one against every editor). T-021 member ranges are
   unaffected — no declaration covers the dropped line — so `--around`
   shares the numbering (L-068). The reader is `JdxService.readSourceLines`
   (`internal`, so the golden suite serves byte-identical lines).
5. **Presentation matches `body`:** `--max-lines 200` default, canonical ref
   is the binary name (`$`-joined nesting), provenance names the *sources*
   file with the logical range (whole file / window / member), `next: jdx
   show <type>`.
6. **`--around` ambiguity is decided from bytecode first (D-009),**
   including the erased→generic-spelling retry (`identity(Object)` finds `U
   identity(U)`) — the same two-step as `executeBody`. A member proven in
   bytecode but absent from sources names T-028; a member unknown to
   bytecode gets did-you-mean (it may be a typo).

**Status:** proposed-by-implementer. Decided 2026-09-20, session 42 (T-023).

### D-037 — `jdx doc` output semantics (T-025) · proposed-by-implementer

**Context:** the fourth M3 CLI slice renders javadoc from paired Java sources
(`sources/.../JavaDocs.kt` extraction, `core/.../render/Doc.kt` rendering,
`JdxService.doc`, thin `DocCommand`). The PROPOSAL only sketches `doc`
(§7.1, Appendix B); the gaps below are pinned here.

**Decisions:**
1. **Under-specified member refs exit 2** (like `body`, unlike `signature`):
   one doc block documents one declaration — a doc that shows many overloads
   is a listing, not documentation.
2. **Only methods inherit docs.** Fields hide rather than override, constructors
   are never inherited, and a superclass's *class* comment describes the
   superclass — serving any of those under the subclass's name would mislead.
   The walk is breadth-first, superclass then interfaces, first-visit-wins
   (the `MemberResolver` linearisation order), and each supertype is read from
   the root that provides *it*, so cross-artifact hierarchies resolve honestly.
   The fallback is labelled on the source line (`(inherited from doc.Base)`)
   plus an `inheritedFrom` JSON key; `next:` still names the queried type.
3. **D-009 strictness holds for undeclared members:** `GrandChild#greet` where
   `GrandChild` declares no `greet` in bytecode exits 1, even when a supertype
   declares it. Inheritance supplies the *comment*, never the member.
4. **`{@inheritDoc}` is replaced with the inherited doc's first paragraph** as
   one line, resolved through the same walk; dropped when `--no-inherited` or
   when no supertype documents the member. One level only.
5. **Rendering is hand-rolled in `core`** (dependency-free by law): a
   conservative known-HTML-tag strip (so `List<String>` in prose survives),
   `{@code}`/`{@link}`/`{@literal}`/`{@value}` unwrapped, block tags kept as
   a tidy block. `--raw` serves the comment content verbatim (leading stars
   intact, blank edges dropped).
6. **Provenance names the sources file that held the comment** (the
   supertype's jar for inherited docs) with the *comment's own* range, not
   the declaration's. The seam splits `TypeNotFound` (unknown nested type →
   T-028 detail) from `TypeUndocumented` (known type, no comment → plain
   exit-1 detail); member unknown-vs-undocumented is split service-side via
   `listJavaMembers` for the same reason.
7. **Flags:** `--inherited` is the default and accepted for explicitness,
   `--no-inherited` disables; both together exit 3. `--max-lines 200`
   truncates whole lines (Appendix B's `doc` row gains `--max-lines`).
   `body`/`members`/`outline --with-doc` stay parked, repointed at the split
   task T-072 — per-row/per-body enrichment is a different scale from
   one-shot `doc`.

**Status:** proposed-by-implementer. Decided 2026-09-20, session 44 (T-025).

### D-038 — Vineflower decompilation semantics (T-026) · proposed-by-implementer

**Context:** T-026 wires PROPOSAL.md §11.2: `body`/`source` reconstruct via
Vineflower when paired sources cannot answer. The gaps are when the fallback
fires, how failures degrade, and how reconstructions are labelled.

**Decisions:**
1. **Fallback fires only when no sources root exists** (bare jars, class
   dirs, JRT without `src.zip`) — plus `--engine vineflower`, which skips
   sources entirely. A *present* root with a missing file or member stays a
   staleness signal (T-028-flavoured detail), never a silent reconstruct:
   the T-023 `stale sources` test pins this, and a sources jar that omits a
   class is evidence about versions, not an invitation to guess.
2. **`.kt`-only roots still name T-039** (Kotlin bodies), even though
   Vineflower could emit Java: facade/class mapping makes that answer
   potentially misleading, and T-039 owns the Kotlin story.
3. **Engine failures are exit 1 naming the javap hatch** (`--engine javap`,
   T-027): a corrupt-for-Vineflower class is not an unreadable artifact
   (exit 5 is reserved for bytes that cannot be read at all).
4. **Provenance names the binary** (`bare.jar`, origin
   `decompiled-vineflower`, the outer `.java` path with the member range),
   and the text line reads `decompiled by vineflower from … ⚠
   reconstructed` (README contract) — the binary jar alone must never read
   as a sources answer.
5. **Loading is lazy and child-first:** Vineflower classes are untouched on
   cache hits and sources answers; the first miss instantiates the runner in
   a child-first loader over the Vineflower jar (falling back in-process
   rather than failing the query). Calls are serialised (engine statics are
   not thread-safe) with a 30 s wall-clock budget on a daemon worker — an
   expired budget abandons the worker and degrades to `Failed`.
6. **Cache is `~/.cache/jdx/decompile/<sha256>-vineflower-<version>.java`**,
   so engine upgrades invalidate automatically. Workspace jars/dirs feed
   `libraries` context via the new `ArtifactRoot.libraryPath` (`jrt:/` has
   no path and contributes none). No goldens pin decompiled text (TESTING.md
   §5.3); the T-021 seam reuse (`MemorySourceRoot` → `findJavaBodies`) is
   what the tests pin instead.

**Status:** proposed-by-implementer. Decided 2026-09-20, session 45 (T-026).

### D-039 — `javap` engine semantics (T-027) · proposed-by-implementer

**Context:** T-027 wires PROPOSAL.md §11.2's second engine: `body`/`source
--engine javap` (the IDE's *Show Bytecode* action). Vineflower produces
Java-like text the T-021 seam can slice; `javap` produces disassembly, which
needs its own member-section matching, and a subprocess brings its own
resolution, versioning and timeout questions.

**Decisions:**
1. **Forced engine only, no auto-fallback.** `--engine javap` skips paired
   sources entirely (like `--engine vineflower`, D-038). A Vineflower failure
   stays exit 1 naming the now-working hatch — it does not silently retry
   through `javap`. Automatic vineflower→javap degradation (TESTING.md §7)
   is filed as T-073; it changes pinned failure semantics and deserves its
   own task, not a drive-by.
2. **Descriptor equality is the member match.** `javap -c -p -s` prints a
   `descriptor:` line per member; the erased descriptor from the
   bytecode-first match (D-009) pairs it with its section — so
   erased-vs-generic query spellings need no retry, and bridge/covariant
   pairs (distinct descriptors) resolve to the first declaration-order
   match, mirroring the `--with-signature` header choice. A proven member
   with no section names T-028, exactly like the sources path.
3. **Section splitting filters the header first.** Real `javap` prints no
   blank line between the class declaration and the first member, so
   blank-delimited blocks would swallow the first member into the header.
   The splitter drops `Compiled from` / `{`-ending / `}` lines, then splits
   the rest on blanks; a block starting with `;` is a member section. The
   `;` rule (not a keyword allowlist) survives field descriptors ending in
   `;`, which never start a block.
4. **Resolution mirrors `doctor`'s check:** explicit override (tests) →
   `$JAVA_HOME/bin` → `java.home/bin` → `PATH`. A missing binary is exit 1
   naming the search ("install a full JDK"), never a throw or an exit 6.
5. **Cache is `~/.cache/jdx/decompile/<sha256>-javap-<version>.java`,**
   where version is the engine's own `javap -version` text (queried once per
   engine instance), so a JDK upgrade invalidates automatically. The version
   probe costs one spawn per instance; repeat disassemblies never re-spawn.
   `javap` is a subprocess, so hostile bytes cannot reach this JVM — and the
   30 s wall-clock budget (daemon reader + `waitFor` timeout, abandoned and
   destroyed on expiry) keeps one hung class from hanging an agent's call.
6. **Presentation is origin-shaped, not engine-shaped:** whole/`--lines`
   `source` serves the full disassembly, `body` and `--around` serve the
   member section, all through the shared `sliceBodyLines`/
   `sliceSourceLines` windowing with `DECOMPILED_JAVAP` provenance
   (`disassembled by javap from … ⚠ reconstructed`). No goldens pin the
   text (TESTING.md §5.3, and it is JDK-version-dependent); tests pin
   sections, exits and determinism instead.

**Status:** proposed-by-implementer. Decided 2026-09-20, session 46 (T-027).

### D-040 — `SOURCES_VERSION_MISMATCH` detection semantics (T-028) · proposed-by-implementer

**Context:** T-028 turns the `WarningCode.SOURCES_VERSION_MISMATCH` enum
(D-009, PROPOSAL.md §11.1) from dead code into an emitted warning on
sources-backed `body`/`source`/`doc` answers. The risk is false positives:
the compiler legitimately widens bytecode beyond sources (synthetics,
bridges, implicit members), and a warning that fires on matched jars trains
agents to ignore it.

**Decisions:**
1. **Warn on success, keep exit codes.** A sources-backed answer whose
   member sets disagree exits 0 with the warning (text `warning
   SOURCES_VERSION_MISMATCH: …` + JSON `warnings[]`); a member proven in
   bytecode but absent from sources stays exit 1 with the code named (no
   `T-028` task ref in user output — the task is done).
2. **Kind-aware pairing** (methods↔methods, `<init>`↔constructors,
   fields/enum-entries↔fields) by name + arity + lenient parameter keys:
   erased descriptor, generic-signature spelling (`U` vs `Object`), and
   varargs/array collapse all normalise to one key. Source extras and
   bytecode omissions are both reported, capped at three refs plus a count.
3. **Compiler output never warns:** synthetic/bridge, `<clinit>`, implicit
   default constructors (no source `<init>` + exactly one bytecode `<init>`),
   record accessors/`toString`/`hashCode`/`equals` and compact↔canonical
   pairing, enum `values()`/`valueOf(String)` and `(String, int)`
   name/ordinal constructor prefix, inner-constructor leading outer-`this`.
   Record components and annotation elements are *declarations* (header
   `Parameters`, `AnnotationMemberDeclaration`) and pair as fields/methods —
   they warn when genuinely removed.
4. **No warning without sources to compare:** decompiled/javap paths,
   `.kt`-only roots and unparseable sources never carry it; their failures
   name the code where a member is proven-but-absent. `show`/`members`/
   `signature` are bytecode-only and unaffected.
5. **Silence is pinned:** every matched fixture type (generics, record,
   enum, annotation, inner, annotated class) asserts no warning in text or
   JSON, so a future widening of either side breaks a test instead of
   spamming agents. Golden files are byte-identical (no warning text added).

**Status:** proposed-by-implementer. Decided 2026-09-21, session 47 (T-028).
