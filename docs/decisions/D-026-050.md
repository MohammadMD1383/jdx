### D-026 — Launcher environment resolution and its exit code (T-004) · proposed-by-implementer

**Context:** the `jdx` launcher (`app/src/main/scripts/jdx`) runs *before* any JVM exists,
so D-015's exit-code contract — written for query results — does not literally apply to its
failures. The task still demands "a human error, not a stack trace".

**Decisions:**
1. Launcher-level failures print one `jdx: <reason>` line on stderr and **exit 6**. Reusing
   D-015's "internal error" keeps the observable contract total: any nonzero exit maps to
   a documented code, so agents can branch without new cases.
2. **A set-but-broken `JAVA_HOME` is a hard error**, not a silent fall-through to `java` on
   PATH. An explicit `JAVA_HOME` is a strong user signal; quietly picking another JDK hides
   the real problem and can inspect bytecode with a different JDK than intended.
3. Resolution order is `JAVA_HOME` → `java` on PATH → `$JDX_JVM_DEFAULT_DIR` (default
   `/usr/lib/jvm/default`, the Arch layout). The override exists mainly so the no-JDK error
   path is testable on machines that always have a JDK, and secondarily for non-Arch users.
4. The minimum JDK is a **hard gate at major 21** (the bytecode target), checked *before*
   exec: an old JDK cannot even load Java-21 class files, and its `UnsupportedClassVersionError`
   stack trace is exactly what this gate exists to prevent.
5. The launcher depends on exactly one external tool, `sed` (checked up front); `dirname` is
   avoided in favour of POSIX parameter expansion and `readlink` is optional, so a broken
   PATH still yields one clean error.

**Status:** proposed-by-implementer. Decided 2026-09-14, session 6 (T-004).
